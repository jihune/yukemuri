## 할 것

1. Wikidata의 한국어·영어 이름(CC0)을 숙소에 붙인다. 연결은 Trip.com ID 같은 정확한 식별자로만 하고, 이름만 비슷하다고 붙이지 않는다(`D06-20261013.md`의 K1, `AGENTS.md`의 다른 숙소를 이름만으로 합치지 않는다는 규칙).
2. D06 지도 좌표처럼 스냅숏을 만들 때 붙여 D1 쓰기를 0으로 둔다. 붙인 이름의 출처를 표시할 수 있게 남긴다.
3. 한국어 이름과 영어 이름이 몇 곳 늘었는지 자료 현황 화면(U06)의 숫자로 확인한다.

## 쓰지 않는 것

- 구글 검색 결과를 자동으로 가져오는 방식: 구글 약관과 이 프로젝트의 수집 안전 규칙에 맞지 않는다.
- LLM 번역·음역: 사용자 결정으로 쓰지 않는다.

## 끝나는 조건

- 병합·배포 뒤 공개 스냅숏에서 한국어·영어 이름 수가 늘어난 것을 확인하고, 잘못 붙은 표본을 점검한 결과를 이 문서에 적었다.

### 2. Wikidata 사용 조건(공식 문서, 10-18T05:58–06:00Z 원문 확인)

- `Wikidata:Licensing`(원문 `action=raw`로 읽음, 페이지 마지막 수정 2026-09-24): ‘All structured data (i.e. the main, Property, Lexeme, and EntitySchema namespaces) is released into the public domain under Creative Commons Zero.’ 레이블·별칭은 항목(main 이름공간)의 구조화 자료라 CC0에 든다. 출처 표시 의무는 없다. 같은 페이지는 CC BY 같은 출처 표시 라이선스를 받지 않는다고 적는다(‘any Creative Commons license other than CC0. This includes Creative Commons Attribution’).
- `Wikidata:Copyright`: ‘All structured data from the main, Property, Lexeme, and EntitySchema namespaces is available under the Creative Commons CC0 License … additional terms may apply.’
- 의무는 없지만 공식 표기를 보장하지 않는 자료라서, 붙인 이름마다 Wikidata 항목 주소를 출처로 남긴다(아래 4).
- 요청 정책: WDQS 사용 설명서(‘Query limits’)는 한 클라이언트(User-Agent+IP)에 60초마다 처리 시간 60초, 오류 질의 분당 30회, IP당 동시 5개를 허용하고, 넘으면 429와 `Retry-After`를 준다. User-Agent 정책은 연락처가 있는 고유한 User-Agent를 요구한다. API 사용량 제한 문서(2026년 새 제한)는 동시 요청 3개 이하와 `Retry-After` 준수를 요구한다. 갱신 스크립트는 SPARQL GET 1회만 보내고 수집 예약에서 부르지 않는다.
- 이 환경에서 Action API(`www.wikidata.org/w/api.php`)는 공유 출구 IP 때문인지 첫 요청부터 429(`Retry-After` 2초, 28초)를 받았다. 그 뒤로 Action API를 다시 부르지 않았다. WDQS SPARQL은 200이었다(무거운 질의 세 번은 502·504로 끝남).

### 3. 정확한 식별자로 잇는 범위

Wikidata 속성 가운데 숙박 예약 사이트 ID는 Booking.com(P3607), Hotels.com(P3898), Expedia(P5651), Agoda(P6008·P10533), Trip.com(P10425) 등이다. Jalan 숙소 ID 속성은 없다(SPARQL로 ExternalId 속성 이름에 hotel·jalan·ryokan·rakuten·onsen·accommodation·lodging이 든 것을 모두 찾음, 10-18T05:57Z). 우리 자료가 가진 공급자 ID는 Trip.com과 Jalan뿐이라 정확히 잇는 길은 Trip.com ID(P10425) 하나다.

- P10425가 있는 항목 43,776개(10-18T05:58Z, 전 세계). 국가(P17)가 일본인 항목은 1,902개, Trip.com ID 1,901개다. 두 항목에 걸린 Trip.com ID는 39개다(빼야 함).
- 우리 Trip.com 기록 1,648곳 가운데 298곳의 ID가 Wikidata에 있다. 그중 296곳이 일본 항목이고 2곳은 국가가 없다.
- 새로 생기는 이름: 한국어 22곳(Wikidata 한국어 레이블 71곳 가운데 우리 한국어 이름이 없는 곳), 영어 1곳(`trip-22678179`). 22곳은 모두 도쿄·요코하마의 대형 호텔이고, 지금 제목이 영어 원어다. 표본 22곳을 손으로 봤을 때 모두 같은 숙소였다(예: `trip-993510` Imperial Hotel, Tokyo → 데이코쿠 호텔, Q712476).
- 일본의 숙박 항목 자체가 적다. P31이 호텔(Q27686)·료칸(Q562930)·온천 료칸(Q11562938)·숙박시설(Q48835818)이고 P17이 일본인 항목은 3,549개, 한국어 레이블이 있는 것은 292개다(10-18T06:03Z, 같은 항목이 두 분류에 있으면 두 번 셈). Trip.com ID가 없는 일본 숙박 항목은 우리 기록과 이을 식별자가 없다.
- 그래서 Wikidata만으로는 한국어 이름이 1,543곳에서 약 1,565곳으로 는다. Jalan 기록(93%)에는 붙일 수 없다. 10-13 D06 조사의 ‘+45’는 그 뒤 Trip.com 한국어 이름 수집이 늘어 22로 줄었다.

### 4. 범위 밖에서 찾은 것(상위 세션·사용자 판단)

- Jalan 자신의 외국어 사이트가 있다. `https://www.jalan.net/kr/japan_hotels_ryokan/`(제목 ‘Jalan : 일본 호텔 & 료칸 예약 사이트’)와 `/en/`·`/cn/`·`/tw/` 등이다. robots.txt(10-18T06:0xZ)는 `/kr/`·`/en/`을 막지 않는다. 숙소 상세 주소 형식과 숙소 번호(yad)가 일본어 사이트와 같은지는 확인하지 못했다(현 목록 쪽은 숙소를 스크립트로 불러 HTML에 yad 번호가 없었다). 같은 번호를 쓰면 Jalan 21,761곳에 공급자의 공식 한국어·영어 이름을 정확한 식별자로 붙일 수 있다. 이것은 새 수집 대상과 수집기 변경이고 D1 쓰기가 생기므로 D07에서 하지 않는다. 이용 약관(`cdn.p.recruit.co.jp/terms/jln-t-1082`)은 읽지 않았다(`jln-t-1083`은 개인정보 처리방침이었다).
- Wikidata의 일본어 레이블로 Trip.com 기록의 원어 이름(지금 영어가 들어 있음)을 채울 수 있다. 위 22곳은 모두 `names.ja`가 영어다. 다만 레이블이 짧은 이름인 경우가 있어(`trip-1489108`의 일본어 레이블 ‘ホテルメトロポリタン’) D07에서는 한국어·영어만 붙인다.

## 설계(D07 PR 1)

1. 추출본: `scripts/update-wikidata-names.mjs`(SPARQL GET 1회, 손으로 실행 뒤 커밋)가 `data/wikidata-trip-names.json`을 만든다. 조건은 P10425와 P17=일본(Q17)이고, 열은 Trip.com ID·항목·한국어 레이블·영어 레이블이다. 한글이 없는 한국어 레이블은 버리고, 두 항목에 걸린 Trip.com ID는 뺀다. D06 좌표 추출본(`data/wikidata-trip-hotels.json`)과 같은 식별자를 쓰지만 파일을 나눈다. 이름 파일은 Worker가 읽어 좌표가 필요 없고, 이름을 갱신할 때 지도 점이 함께 바뀌지 않게 하려는 것이다.
2. 붙이는 규칙(`lib/wikidata-names.ts`): `trip-<숫자>` 기록이 추출본에 정확히 있을 때만 붙인다. 한국어는 기록에 한글 이름이 없을 때만, 영어는 기록에 영어 이름이 없을 때만 넣는다. 수집한 이름이 늘 먼저다. 원래 이름은 별칭에 남긴다. 출처는 `sources`에 Wikidata 항목 주소(`https://www.wikidata.org/wiki/Q…`)로 한 줄 더한다. 상세의 ‘정보 출처’가 이 줄을 그대로 보여 준다(화면 파일은 고치지 않음). 한국어를 붙이면 `nameLocaleUrl`도 둔다(‘한국어 숙소명 출처’ 링크).
3. 붙이는 곳: 스냅숏 생성(`lib/search-snapshot-build.ts` 숙소 훑기)에서 카드·검색 이름·`core.name`·자료 현황 집계에, 상세·비교 API(`lib/hotel-repository.ts` `getMany`)에서 응답에 붙인다. 둘 다 읽기만 하므로 D1 읽기·쓰기는 그대로다(새 질의 없음). 수집 경로(`writeHotels`)와 수집 예약은 바꾸지 않는다. D1 `hotels.name`·`search_text`도 그대로다.
4. 대조 검사(`scripts/check-wikidata-names.mjs`): 규칙 검사(정확한 ID만, Jalan 같은 번호는 안 붙음, 수집 이름이 이김, 한글·영어 조건, 출처 줄)와 대조군, 추출본 무결성을 `cloud-check.py`에 넣는다. `--public`은 공개 스냅숏에 같은 규칙을 적용해 붙는 숙소를 모두 나열하고, Wikidata 좌표(D06 추출본)와 우리 좌표의 거리, 영어 레이블과 우리 영어 이름의 단어 겹침으로 잘못 붙은 표본을 찾는다. 일부러 다른 항목을 붙인 대조 표본이 걸리는지도 본다.
5. PR 나눔: 위 1~4를 PR 하나로 연다. 병합·배포 뒤 공개 `status.json`과 `--public` 점검 결과를 이 문서에 적는 기록 PR은 상위 세션 몫이다(결과는 이 세션이 문서에 적어 넘김).
