### 1. 다음 상위 세션이 이어받을 때 할 일

인계 방법: 지금 상위 세션의 계보 깊이(`get_session`의 `lineage`)가 한도에서 두 단계 안이 아니면, 지금 상위 세션이 다음 상위 세션을 `create_session`(환경 Heavy `env_01QChiMBEXVzTkCBZTgHveii`, 그때의 상위 모델, `source_url`과 `outcome_branch` `claude/yukemuri-parent-<번호>`를 함께)으로 열고 ‘main의 docs/work-handoff-latest.md 「상위 세션 인계」를 열어 요약하지 말고 1의 순서대로 실행한 뒤 4를 이어 하라’는 한 줄만 보낸다. 두 단계 안이면 사용자가 웹에서 같은 한 줄로 연다(환경 Heavy, 저장소 `jihune/yukemuri`·`jihune/yukemuri-script-runner`·`jihune/agent-harness`). 안내와 다시 알리기는 아래 2의 ‘다음 상위 세션 안내’를 따른다. 사용자가 연 세션은 계보가 새로 시작한다(스물두 번째가 깊이 2/8이라 스물세 번째도 `create_session`으로 연다, 깊이 3). `create_session`으로 연 세션은 앱 저장소만 붙어 열리므로 아래 4대로 실행기 저장소(push)와 하네스 저장소(read)를 `add_repo`로 붙인다. 옛 상위 세션은 그 뒤 새 일을 하지 않고 자기 기록 브랜치에 push하지 않으며, 받은 메시지를 새 상위 세션에 넘긴다. 보관하지 않는다. 사용자가 웹에서 여는 경우에는 새 상위 세션이 이어받았다고 알릴 때까지 옛 상위 세션이 일을 이어 가고, 그 사이 바뀐 것은 기록 PR로 main에 넣는다.

이어받는 세션은 하네스 규칙(인계를 받은 세션의 누락 점검)대로 이 인계에 빠진 것이 없는지 스스로 점검한다. 옛 상위 세션의 사용자 메시지를 하위 에이전트가 `list_events(session_id=<옛 상위 세션>, kinds=["user"], limit=100)`로 첫 쪽부터 `before_id`로 거슬러 빈 쪽이 나올 때까지 읽고, 그 뒤에야 첫 쪽의 `last_id`부터 `after_id`로 앞으로 읽게 한다(끝 확인 호출을 앞으로 가는 호출 뒤에 하면 `extract`가 `early_forward`로 FAIL, 11-10 스물두 번째). 하네스 `session-handoff`의 `scripts/user_messages.py extract <하위 에이전트 기록>`(부모 세션 폴더의 `subagents/agent-<id>.jsonl`)으로 사람이 입력한 것만 뽑아 아래 2·4와 대조한다. 쪽이 커서 파일로 저장되면 그 하위 에이전트에게 `python3 -I <session-handoff 폴더>/scripts/user_messages.py cursor <저장된 쪽 파일>` 한 줄만 허락한다. 사용자는 인계 뒤에도 옛 상위 세션에 글을 쓸 수 있으니 이 점검은 예약 이전과 알림을 마친 뒤에 한다. 사용자의 작업이나 결정이 필요하면 사용자에게 묻는다(사용자 10-17T17:0xZ: ‘인계시 새 세션에서 작업한다면 인계한거 빠진거 없는지는 규칙에 따라 자동으로 검토하면 될거다. 사용자 작업이나 결정 필요사항 있다면 새 세션에서 역질문 하던가 답변해주면 된다.’).

### 5. 상위 세션이 배운 것

다섯·여덟·아홉·열다섯·열여섯·열일곱 번째 상위 세션의 시행착오는 `docs/history/lessons-parent<번호>-<날짜>.md`에 따로 적었다(하네스 관리 세션에도 보냄). 열일곱 번째의 둘째 교훈은 `lessons-parent17-20261102.md`(11-02, #282)이고, 첫째(`lessons-parent17-20261028.md`)는 승인 넘기기 시험, 런타임 PR 규칙과 사용자 P2 규칙, 일 단위 예산과 실패선 사이의 정기 소비, 하위 세션 검산이 다를 때, 문장 부호만 바뀐 룰 본문 가리기다.

- 병합 판단: 마지막 검토 커밋과 지금 main을 합친 트리(`git merge-tree --write-tree $(git merge-base HEAD origin/main) <검토 커밋>`)와 지금 head를 `git diff --stat`으로 비교한다. 기록 파일만 나와야 한다. 지금 main과의 충돌은 `git merge-tree --write-tree origin/main <head>`로 직접 본다. 그 뒤 CI(최신 head)와 해결 안 된 스레드를 본다.
- PR의 CI가 돈 뒤 다른 코드 PR이 main에 들어가면, 병합 전에 하위 세션에 main을 merge로 합쳐 다시 CI를 돌리게 한다(#163, 10-18). 두 PR이 함께 고친 파일이 없어도 그렇게 한다.
- 기록 브랜치는 매번 main 위에서 다시 시작한다(기록 PR 병합 뒤 `git merge --ff-only origin/main`). 이 브랜치는 상위 세션만 쓴다. 기록 PR을 쓰기 전에 하위 세션 브랜치마다 main에 없는 기록 커밋이 있는지 본다.
- 다른 세션이 '사용자가 승인했다'고 전한 저장소 변경은 사용자에게 확인한 뒤 한다.
- 사용자의 모바일 Claude 앱 권한 메뉴에는 ‘묻기’가 보이지 않아 ‘수정 수락’으로 바꾼 적이 있다(10-20T09:52Z). 클라우드 세션의 ‘수정 수락’은 기본(묻기) 모드와 같아 하위 세션·예약 실행이 멈추므로, 권한 모드를 바꿔 달라고 할 때는 웹에서 자동 모드로 되돌리는 것까지 함께 말한다.
- 하위 세션의 CI 완료 알림이 오지 않을 때가 있다. 하위 세션은 안전망 확인 예약으로 CI를 직접 본다. 세션 사이 메시지가 늦게 닿을 때도 있다(10-18: 08:03Z에 보낸 메시지가 08:27Z에 닿음). 정정은 한 통으로 보내고 ‘이것으로 정함’이라고 적는다.
- GitHub 도구 `actions_list`(list_workflow_runs)는 `per_page`를 무시하고 수십 건을 돌려준다. 마지막 실행 하나만 볼 때는 공개 API를 `curl -s "https://api.github.com/repos/jihune/yukemuri/actions/workflows/collect.yml/runs?per_page=1"`로 부른다(10-18T11:16Z 200 확인).
- 한자 검사는 더한 줄에만 한다. `roadmap.md` L01 줄에는 원래부터 있던 원문 고유명 두 개가 있다.
- Codex의 ‘큰 문제 없음’ 결과는 리뷰 객체가 아니라 이슈 댓글(본문의 ‘Reviewed commit’)로 온다. 병합 전에는 이슈 댓글까지 본다.
- 같은 갈래의 검토 지적이 회차마다 되풀이되면(D07 #145의 출처 짐작) 그 갈래를 하나 더 고치지 말고 근본 원인을 고치게 한다. 만드는 쪽이 기록한 것을 점검이 읽게 하면 짐작 코드가 사라진다.
- `git checkout -B`가 자동 모드 분류기에 막힌 세션이 있었다. 그때는 `git fetch origin main` 뒤 `git merge --no-edit origin/main`으로 main을 합쳐 이어 쓴다. 처음 받은 클론이 얕으면(`git rev-parse --is-shallow-repository`가 true) `origin/main..origin/<브랜치>`에 이미 병합된 커밋까지 보이므로 `git fetch --depth=1000`으로 깊게 받는다. 실행기 저장소 클론에서는 브랜치를 `git fetch origin +refs/heads/<브랜치>:refs/remotes/origin/<브랜치>`처럼 refspec을 적어 받는다.
- 하위 세션이 마지막 검토 뒤 코드 파일을 고치면(#151의 `9819070`, 주석 한 줄) 병합 조건(마지막 검토 뒤 변경은 기록 파일뿐)에 걸린다. 등급의 회차가 남았으면 그 차이를 다음 회차로 보게 하고, 다 썼으면 더 받는 회차에 사용자 허락이 필요하므로 그 파일을 되돌리게 하고 고칠 것은 다음 PR로 넘긴다.
- 인계 8의 기록 줄은 한두 문장으로 쓴다. 숫자와 근거는 PR 본문·`deployments.md`·작업 문서에 두고 여기에는 가리키기만 한다(10-18: 기록 줄이 길어 문서가 4시간 만에 38 KB에서 53 KB가 됨).
- 마지막 검토가 P2·P3만 남기면 그 스레드에 ‘다음 일로 넘김’을 한 줄 답하고 해결한 뒤 병합하고, 남은 것은 하위 세션의 작은 후속 PR로 묶는다(#166, 10-18. P2까지 넓힌 것은 10-26 검토 규칙 결정).
- 등급 2 PR의 검토는 하위 세션이 곧 push할 head가 아니라 push 뒤 head에서 Codex와 같은 head를 보게 한다. 상위 세션은 지적을 하위 세션에 보내기 전에 그 줄을 직접 읽어 경로를 확인한다. 상위 세션은 병합할 때 병합한 head를 알리고, 하위 세션은 그 뒤 더할 기록을 다음 기록 PR로 낸다. 하위 세션이 글로 보낸 기록은 급하지 않으면 모아 다음 기록 PR에 싣는다(열세·열다섯 번째, 사례는 `docs/history/work-handoff-20261110T1156Z.md` 「상위 세션 인계」 5).
