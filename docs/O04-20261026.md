# O04 — 매일 점검과 DB 백업을 바깥 예약기로 부르기(두 번 돌지 않게)

기록: 2026-10-26T12:5xZ, 열두 번째 상위 세션 `session_01SarDBHKWzi47RJ6veCY6oi`. 상태: 맡기기 전. 이 문서는 첫 brief이고, 맡은 세션이 설계·검사·결과를 아래 ‘진행 기록’에 이어 적는다.

## 왜 하는가

- 사용자 결정(2026-10-21T07:3xZ, `roadmap.md` 결정 기록 ‘C06 겹침 막기·남은 후보·바깥 예약기’의 3): 매일 점검과 DB 백업을 GitHub 예약 대신 바깥 예약기(Cloudflare Workers Cron 등 무료)로 부르고, GitHub 예약과 두 번 돌지 않게 막는 장치를 함께 넣는다. 원문 ‘바깥 예약기로 옮김, 중복 막는 코드 추가를 하면 완성도가 더 높고 오류 발생 확률도 떨어지고, 최적화도 가능하다면 당연히 하는게 맞음.’
- GitHub `schedule`이 늦거나 빠진다. 실행기 저장소 예약의 실제 시각은 다음과 같다.
  - 매일 점검 `Yukemuri daily check`(cron `41 1 * * *`): 10-19 5시간 8분 늦음, 10-20 4시간 55분 늦음, 10-22–10-26은 06:27Z–06:58Z(약 5시간 늦음). 모두 성공했다(`O03-20261019.md`, `work-handoff-latest.md` 「상위 세션 인계」 3).
  - DB 백업 `Yukemuri private database backups`(cron 19:23Z): 10-21–10-25에 21:39Z–22:24Z(2–3시간 늦음). 모두 성공했다.
  - 수집 부르기 ‘Yukemuri catalog updates’는 cron이 3시간마다든 매시간이든 하루 5번만 왔다(10-14–10-19, `docs/evidence/h01-schedule-gap-20261018/`).
- 바깥 자료(10-20 상위 세션이 원문을 읽음, `docs/history/work-handoff-20261020T0627Z.md` 「상위 세션 인계」 8의 10-20T04:39Z): GitHub 문서 ‘Events that trigger workflows’의 `schedule` 절은 ‘The `schedule` event can be delayed during periods of high loads … If the load is sufficiently high enough, some queued jobs may be dropped.’라고 쓰고, 권하는 조치는 정각을 피하는 것뿐이다.
- 지금은 예약이 늦어도 그날 안에 와서 문제가 드러나지 않았다. 예약이 빠지면 그날 백업이 없고, 매일 점검이 빠지면 아무도 보지 않는다(백업이 빠진 날은 다음 매일 점검이 실패로 알리지만, 매일 점검 자신이 빠진 날은 알릴 곳이 없다).
- 하네스 `cloud-session-ops` §4(하네스 `5f8c5b4`): ‘A `schedule` trigger can fire late or not at all under load. A job that must not miss a window scans back from its last successful run, not over a fixed span, since a dropped run leaves a whole period, and reports its own runs (`actions: read`), so a skipped day shows.’ 같은 하네스 `cloudflare-free-tier` §5는 두 번째 트리거를 둘 때 일이 한 번만 돌게 하는 방법(빠진 칸에만 돌거나, 이미 한 칸은 건너뜀)을 함께 정하라고 쓴다.

## 할 것

1. 바깥 예약기를 고르고 설계한다(구현 전에 조사). 후보는 셋이다.
   - (가) 앱 Worker(`jihune/yukemuri`의 운영 Worker)에 Cron Trigger와 `scheduled` 처리기를 더해, 실행기 workflow의 `workflow_dispatch`를 부른다.
   - (나) 실행기 저장소(private)에서 배포하는 작은 Worker를 따로 둔다.
   - (다) 그 밖의 무료 바깥 예약기. 사용자 결정은 ‘Cloudflare Workers Cron 등 무료’다.
   - 비교할 것: Workers Free의 Cron Trigger 수·실행 제한(Cloudflare 문서 원문과 읽은 날짜, 하네스 `source-freshness`), GitHub 토큰을 어디에 두는지(public 앱 저장소의 코드와 Worker Secret, private 실행기), 배포 경로와 그 배포가 D1을 읽는지, 바깥 예약기 자체가 실패하면 무엇이 그것을 알리는지(Worker의 예약 실행 실패는 메일이 가지 않는다).
   - 권장안 하나를 이유와 함께 이 문서에 적고 상위 세션에 보낸다. 새 Secret이나 사용자 작업이 필요하면 구현 전에 그 단계를 함께 보낸다(아래 ‘지켜야 할 것’).
2. 부르는 대상은 실행기의 `yukemuri-daily-check.yml`과 `yukemuri-backup.yml`이다. workflow 자체는 GitHub에 그대로 두어 실패 메일 경로를 지킨다. 백업은 개인 즐겨찾기가 든 artifact를 만들므로 private 실행기에 남는다(`AGENTS.md` ‘레포 구조 계획’). 부르는 시각은 정각·30분을 피하고, 매일 점검은 앞날 마지막 수집과 그 스냅숏 배포가 끝난 뒤(O03이 고른 01:41Z의 까닭), 백업은 지금 cron(19:23Z)의 까닭과 그날 D1 읽기 예산을 함께 보고 정한다. 백업의 D1 읽기가 수집 예산(`collection-budget.mjs`)에 어떻게 잡히는지 확인해 적는다.
3. 두 번 돌지 않게 한다. GitHub `schedule`은 예비로 남긴다(하네스 줄대로 두 번째 트리거가 된다).
   - 각 workflow는 시작할 때 자기 칸을 정한다(매일 점검은 보는 날 = 실행 시각의 어제 UTC, 백업은 그 UTC 날). 자기 실행 목록을 마지막 성공 실행부터 거슬러 보고, 그 칸이 이미 끝났거나 진행 중이면 할 일을 하지 않고 성공으로 끝내며 요약 한 줄(‘이미 run N이 함’)을 남긴다.
   - 거의 같은 때 두 트리거가 오면 GitHub `concurrency` 묶음(`queue: max`, `cancel-in-progress: false`, 하네스 `cloudflare-free-tier` §6)으로 줄을 세워, 뒤 실행이 앞 실행의 결과를 보고 건너뛰게 한다.
   - ‘끝났다’의 뜻을 정한다. 매일 점검은 그날을 판정한 실행(통과든 실제 값 때문에 실패든)을 끝난 것으로 본다. 그래야 실제 문제로 실패한 날 실패 메일이 두 번 가지 않는다. 판정 전에 실패한 실행(부르기·읽기 오류)은 끝난 것으로 보지 않는다. 백업은 `backup` job이 성공한 실행만 끝난 것으로 보므로, 실패한 백업은 두 번째 트리거가 다시 한다.
   - 매일 점검의 백업 판정(`scripts/backup-status.py`, 지금은 `event`가 `schedule`인 실패와 main의 성공을 셈)이 바깥 예약기의 `workflow_dispatch` 실행과 건너뛴 실행을 맞게 세도록 고친다.
4. 실행마다 요약에 누가 불렀는지(event, actor, 바깥 예약기면 그 표시)와 의도한 시각에서 늦은 정도를 남긴다. 나중에 바깥 예약기가 몇 번 왔고 예비 예약이 몇 번 일했는지 셀 수 있어야 한다.
5. 검사와 대조: 건너뛰기 판정에 가짜 실행 목록을 넣는다(이미 끝난 칸은 건너뜀, 진행 중은 건너뜀, 판정 전 실패는 다시 함, 다른 날 실행은 무시, 실패한 백업은 다시 함). 임시 사본에서 규칙을 한 군데씩 고장 내 검사가 실패하는지 본다. Worker 쪽은 가짜 `fetch`로 부르기 요청(주소, 본문, 토큰을 찍지 않음, 응답 204가 아니면 실패로 기록)을 검사한다. workflow는 actionlint로 본다.
6. 끝나는 조건: 병합·배포 뒤 UTC 사흘 동안 바깥 예약기가 두 workflow를 의도한 시각 가까이 불렀고, 그날 온 예비 `schedule` 실행은 건너뛰었으며(또는 바깥 예약기가 빠진 날에만 일했으며), 백업이 하루 두 번 돌지 않았고, 매일 점검이 그날을 한 번만 판정했음을 run id와 함께 이 문서에 적는다.

## 지켜야 할 것

- 무료 요금제만 쓴다. Workers Paid로 바꾸지 않는다. 실행기 Actions 분은 월 무료 범위 안이어야 한다(`cloud-development.md` ‘CI와 Actions 사용 시간’).
- 바깥 예약기가 GitHub를 부르려면 새 토큰이 필요할 가능성이 크다. Secret과 토큰은 사용자가 만든다(`AGENTS.md`). 최소 권한(필요한 저장소만, Actions 읽기·쓰기, 만료일)으로 설계하고, 만들 곳·이름·권한을 상위 세션에 보낸다. 상위 세션이 사용자에게 묻는다(하네스 `credential-setup-guide`). 값은 채팅·로그·PR·문서에 쓰지 않고, 사용자는 ‘완료’만 알린다.
- 수집 workflow·실행기 수집 예약·수집 상한은 바꾸지 않는다(`AGENTS.md` ‘수집 주기/상한 변경은 이번 범위에 포함되지 않는다’). 같은 바깥 예약기를 수집 고리(C06)의 예비로도 쓸 수 있으면 이 문서에 제안으로만 적는다.
- 앱 저장소 코드 PR은 병합하면 배포가 한 번 돌아 스냅숏 생성 읽기(약 14.6만 행, 하루 읽기 한도의 약 2.9%, `deployments.md` 10-26 줄)를 쓴다. 한 UTC 날에 코드 병합은 하나만 하고 날짜는 상위 세션이 정한다(10-27 #244, 10-28부터 C07 방안 2가 먼저 잡혀 있음). Worker 설정을 바꾸면 하네스 `cloudflare-free-tier` §6(Secret은 `--secrets-file`로)을 따른다.
- 두 저장소의 코드 PR은 같은 검토 규칙을 따른다(`AGENTS.md` 병합 조건의 위험 등급, 10-26T13:3xZ 사용자 결정, 실행기는 `project-files.json` 갱신). PR은 상위 세션이 병합하고 병합 기록을 쓴다.
- 운영 DB를 개발 환경에 연결하지 않는다. 운영 확인은 공개 GET과 이미 있는 읽기 전용 조회만 한다. 백업 workflow를 손으로 더 돌려 D1을 읽지 않는다(시험은 가짜 자료나 `workflow_dispatch`의 검증 경로로).
- 사용량 기준은 5시간 창 0.9, 7일 창 0.95다. 닿으면 하던 단계만 커밋·push하고(끝나지 않은 수정은 ‘WIP:’ 커밋), PR 구독을 풀고, CI·Codex·세션 메시지에 자동으로 답하지 않으며, 기준을 넘은 창 가운데 가장 늦은 `resetsAt`의 10분 뒤 재개 예약 하나만 남기고 상위 세션에 알린다.

### 1. 조사(10-26T13:0xZ)

- Cloudflare 문서(`developers.cloudflare.com/workers/platform/limits/index.md`·`/workers/configuration/cron-triggers/index.md`·`/workers/runtime-apis/handlers/scheduled/index.md`, 10-26T13:01Z `curl`로 원문 받음). Workers Free에서 계정당 Cron Trigger는 5개, Cron 실행 한 번의 CPU는 10 ms, 실행 시간은 15분, 실행 한 번의 subrequest는 50개다. Cron 설정을 바꾸면 반영까지 최대 15분 걸린다. Cron은 UTC로 돈다. Worker 하나에 Cron을 여럿 두면 같은 `scheduled()` 처리기가 불리고 `controller.cron`으로 구분한다. 실패한 예약 실행을 Cloudflare가 다시 부르는지는 이 문서들에서 찾지 못했다(`controller.noRetry()`가 있다는 것만 확인). 그래서 GitHub 쪽 건너뛰기가 같은 칸의 두 번째 부르기를 언제나 막아야 한다.
- 앱 Worker의 지금 설정(`dist/server/wrangler.json`, `vite.config.ts`가 만듦)에는 `triggers`가 비어 있다. 계정의 다른 Worker가 Cron을 쓰는지는 이 세션에서 볼 수 없다.
- 실행기 Secret: `CLOUDFLARE_API_TOKEN`·`CLOUDFLARE_ACCOUNT_ID`가 이미 있다. `cloudflare-deploy.md` 3단계 ‘1. API 토큰’·‘2. GitHub Secret’에 따르면 앱과 같은 사용자 토큰이다(템플릿 ‘Edit Cloudflare Workers’에 D1 Edit·Account Analytics Read를 더함). 문서상 그 토큰으로 실행기에서 Worker를 올릴 수 있지만, 같은 값이 들어 있는지는 첫 배포 실행에서 확인된다. 실행기의 `YUKEMURI_APP_DISPATCH_TOKEN`은 앱 저장소만 대상이라 실행기 workflow를 부를 수 없다.
- 백업의 D1 읽기: 백업은 앱 Worker의 `/api/catalog-export`를 쪽 단위로 읽는다(`lib/catalog-export.ts`). 표마다 시작과 끝에 `COUNT(*)`를 한 번씩 하고(`countsBefore`·`countsAfter`) 행을 한 번 읽는다. 10-25 백업(실행기 run 40237467957)은 13개 표에서 105,723행을 내보냈다. 그래서 백업 한 번은 약 3배인 31–32만 행(하루 읽기 한도의 약 6.3%)을 읽는다고 어림한다. 직접 잰 값은 아니다. 수집 예산(`collection-budget.mjs`)은 백업 몫을 따로 빼지 않는다. 실행마다 그날 이미 쓴 읽기를 다시 읽고 한도의 85%까지만 쓰며, 남는 15%가 백업·배포·방문자 몫이다(`share` 주석). 백업이 수집 실행보다 먼저 돌면 그 뒤 실행의 쪽수가 줄고, 마지막 수집 뒤에 돌면 15% 안에서 쓴다.
- 지금 예약 시각: 매일 점검 cron 01:41Z(전날 마지막 수집과 그 스냅숏 배포가 끝난 뒤, `yukemuri-daily-check.yml` 주석). 백업 cron 19:23Z(04:23 KST, `db-backups.md`). 실제로는 매일 점검이 약 5시간, 백업이 2–3시간 늦게 왔다(위 ‘왜 하는가’).

### 2. 설계 권장안(10-26T13:0xZ, 상위 세션에 보냄)

권장: (나) 실행기 저장소에서 배포하는 작은 예약 Worker `yukemuri-scheduler`. 앱 저장소 코드는 바꾸지 않는다.

- 까닭:
  - 실행기 workflow를 부르는 토큰은 실행기 Actions 읽기·쓰기 권한이 있어야 한다. 이 권한으로는 백업 artifact(개인 즐겨찾기 포함)를 내려받거나 지울 수 있다. (가)는 이 토큰을 public 앱 저장소의 Secret과, 누구나 부르는 운영 Worker에 둔다. (나)는 private 실행기 Secret과, HTTP 주소가 없는 Worker에만 둔다.
  - (나)의 Worker에는 D1 바인딩이 없어 배포와 실행이 D1을 읽지 않는다. (가)는 예약을 고칠 때마다 앱 배포(스냅숏 생성 읽기 약 14.6만 행)가 돌고, 앱 롤백이 예약 처리기도 되돌린다.
  - ‘예약은 private 실행기에 둔다’는 지금 구조(`yukemuri-catalog.yml` 첫 주석)와 같다.
