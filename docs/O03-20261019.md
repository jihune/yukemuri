### 실행기 PR 설계(상위 세션 요청, 10-18T01:3xZ)

1. 새 workflow 하나, job 하나: `.github/workflows/yukemuri-daily-check.yml`, 이름 ‘Yukemuri daily check’.
   - `on`: `schedule` `cron: '41 1 * * *'`(매일 01:41Z, 10:41 KST)와 `workflow_dispatch`. 0분·30분을 피했다. 앞날 23:5xZ에 시작한 수집(약 25분)과 그 스냅숏 배포가 끝나고, Cloudflare 분석 자료가 찬 뒤다. GitHub 예약이 몇 시간 늦어도 앱 점검은 실행 시각 기준 ‘어제’를 본다.
   - `permissions`: `contents: read`, `actions: read`(자기 저장소의 백업 실행 읽기). `timeout-minutes: 3`.
   - `YUKEMURI_ENABLED`는 보지 않는다. 수집을 멈춘 동안에도 사용량과 백업은 봐야 한다. 수집을 멈춘 날은 앱 점검의 gentle 표가 0회가 되고 실패로 보지 않는다.
2. 단계 1 — 앱 점검 부르기: 기존 부르기 토큰(대상 `jihune/yukemuri`, Actions: Read and write)으로 `POST https://api.github.com/repos/jihune/yukemuri/actions/workflows/usage.yml/dispatches`, 본문 `{"ref":"main","inputs":{"check":"true"}}`. `date`와 `control`은 보내지 않는다(어제, `none`). 응답이 204(또는 run 정보를 주는 200)가 아니면 실패한다. 응답 본문과 토큰은 찍지 않는다. 앱 점검의 판정은 앱 run이 스스로 실패로 끝나 메일을 보내므로 실행기는 기다리지 않는다(실행기 분을 아낀다).
3. 단계 2 — 전날 백업 확인(`if: ${{ !cancelled() }}`, 단계 1이 실패해도 돈다): `github.token`으로 `GET /repos/jihune/yukemuri-script-runner/actions/workflows/yukemuri-backup.yml/runs?created=<어제>T00:00:00Z..<지금>&per_page=100`.
   - 창은 어제 00:00Z부터 지금까지다. 백업 cron(19:23Z)이 GitHub 지연으로 자정을 넘겨도(실측 21:30Z–23:18Z) 창 안에 든다.
   - `event`가 `schedule`인 끝난 실행 가운데 `conclusion`이 `success`가 아닌 것이 하나라도 있으면 실패, 끝난 성공 실행(예약·수동 모두 셈)이 하나도 없으면 실패다. 진행 중인 실행은 판정하지 않는다.
   - `GITHUB_STEP_SUMMARY`에 표(run id, 만든 시각, event, 결과)와 판정을 쓰고, 실패면 `::error::`를 남긴다. 실행기는 private이지만 비밀값은 찍지 않는다.
4. 검사: 실행기의 기존 검사 방식으로 백업 판정 함수에 가짜 실행 목록을 넣어 본다(성공 하나 → 통과, 예약 실패 → 실패, 성공 없음 → 실패, 진행 중만 → 실패(성공 없음), 창 밖 실행 무시). 대조로 판정 하나를 고장 내 검사가 실패하는지 본다. workflow는 actionlint로 본다.
5. Actions 분: job 하나가 하루 1분 안이다. 월 약 30분으로 지금 실행기 사용(약 400분/월)에 더해도 2,000분 안이다.
6. 끝나는 조건과의 관계: 실행기 PR 병합 뒤 `workflow_dispatch`로 한 번 돌려 앱 `usage.yml` run(`Cloudflare usage (daily check)`)이 생기는지 본다. 앱 점검은 실행 시각 기준 어제(UTC)를 보므로, 10-17처럼 쓰기가 85%를 넘은 날이면 실패해야 한다. 정상인 날 성공은 앱 `usage.yml`을 `check: true`, `date: 2026-10-16`으로 수동 실행해 본다.
