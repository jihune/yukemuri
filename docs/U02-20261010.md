- 체크인된 1,655개 중 좌표가 있는 기록은 57개다(`lib/hotels.real.json`·`hotels.crawled.json`·`hotels.verified.json`을 id 기준으로 직접 셈). 지도에 나올 수 있는 숙소가 적은 주된 원인은 좌표 없음이다. 운영 D1은 2026-10-08T16:25Z 체크포인트에서 기록 12,155개 중 좌표 1,276개였다(`roadmap.md`의 ‘C01 종료 집계’). 현재 운영 값은 확인하지 않았다.
- Trip.com 8.0 이상 조건: 결과 44곳. 미확인 때문에 제외된 후보는 1,610곳이다. 대부분 Trip.com 평점이 없는 기록이다.
- ‘내 검증 기준’(Trip.com 9.0+, 리뷰 50개+): 결과 25곳, 미확인 제외 1,610곳.
- 조건 없는 첫 쪽 40곳 중 좌표가 있는 숙소는 35곳이었다.

## 변경

1. API 응답 `SearchResponse`에 `unknownExcluded`를 더했다. 같은 지역·검색어·휴업 제외 범위에서 선택한 시설·평점·리뷰 조건을 하나도 어기지 않았지만 그중 하나 이상이 미확인이라 결과에서 빠진 숙소 수다. 확인된 ‘없음’이나 기준 미달이 하나라도 있는 숙소는 세지 않는다. 기존 집계 쿼리에 합계 한 열을 더했으므로 요청 수는 늘지 않는다. 결과 세션(쪽 넘김)에도 같은 값을 저장한다. 미확인 숙소는 결과에 넣지 않고 정보를 추정해 채우지 않는다.
2. 목록 위에 ‘선택한 조건 중 확인되지 않은 정보가 있어 제외한 숙소가 N곳 더 있습니다. 미확인 정보는 추정하지 않습니다.’를 표시한다. 검색 중이거나 검색이 실패하면 숨긴다.
3. 지도 열 위에 ‘검색 결과 N곳 중 지도에 M곳 표시’, ‘불러온 X곳 중 위치 미확인 Y곳’, ‘아직 불러오지 않음 Z곳’을 표시한다. 결과가 모두 지도에 있으면 한 문장으로 줄인다. 결과가 0이고 다른 후보만 있으면 그 사실을 쓴다. 휴대폰 지도 화면에서도 보인다.
4. 같은 줄에 ‘40곳 더 불러와 지도에 표시’ 버튼을 두었다. 불러오는 중에는 버튼 문구가 바뀌고 `aria-disabled`가 된다. 실패하면 오류 문장(`role=alert`)과 ‘다시 불러오기’로 바뀐다. 버튼을 다시 그리지 않으므로 키보드 포커스가 유지된다.
5. 지도 캡션을 ‘불러온 숙소’에서 ‘지도 표시’로 고쳤다. 수는 좌표가 있는 숙소 수 그대로다.

바꾼 파일: `lib/hotel-repository.ts`, `components/hotel-explorer.tsx`, `components/use-hotel-results.ts`, `components/stay-map.tsx`, `app/globals.css`. DB 스키마·마이그레이션·수집기는 바꾸지 않았다.

## 지도 범위 검색 설계

구현하지 않았다. 범위와 순서를 확정한 뒤 별도 작업으로 진행한다.

### 목표

사용자가 보고 있는 지도 범위 안에서, 현재 조건을 만족하는 숙소 전체의 위치를 보여 준다. 불러온 목록 쪽수와 관계없이 동작해야 한다.

### 전체 좌표 조회 방식

- 새 엔드포인트 `GET /api/hotels/map`을 둔다. 기존 검색과 같은 조건 인자(`region`·`q`·`features`·`rating`·`reviews`·`ryokan`·`saved`)에 `bbox=서경,남위,동경,북위`를 더한다.
- 응답은 숙소 전체가 아니라 지점 목록이다: `id`, 위도, 경도, 선택한 출처 평점. 같은 조건의 `total`, 범위 안 수, 범위 밖 수, 좌표 없음 수를 함께 준다. 지점을 누르면 기존 상세 API로 숙소를 연다.
- 조건 쿼리는 `searchHotels`의 `WHERE` 구성을 그대로 재사용한다. 결과가 달라지지 않게 한 함수에서 만든다.
- 좌표는 지금 `payload` JSON 안에만 있다. 1단계는 `json_extract(payload,'$.location.latitude')`로 읽는다. 스키마를 바꾸지 않는다. 쿼리 시간이 문제가 되면 2단계에서 `latitude`·`longitude` 열과 색인을 마이그레이션으로 더한다. 이때 `writeHotels`와 백업 실행기의 복원 스키마(`docs/db-backups.md`)도 함께 바꾼다.
- 운영 D1에서 `json_extract` 쿼리 시간은 측정하지 않았다. 1단계 PR에서 운영과 같은 규모의 임시 DB(기록 약 12,000개)로 측정한다.

### 요청 상한

- 지도를 움직일 때마다 자동으로 요청하지 않는다. 지도를 움직이면 ‘이 지역에서 검색’ 버튼을 보이고, 누를 때만 요청한다.
- 한 응답의 지점은 최대 500개로 둔다. 넘으면 지점 대신 격자별 개수(위도·경도를 줌에 맞춰 반올림한 묶음)를 돌려주고 ‘확대해 주세요’를 안내한다. 이 숫자는 설계 값이며 측정 뒤 조정한다.
- 진행 중인 요청은 새 요청이 오면 취소한다(`AbortController`). 같은 조건·범위의 응답은 기존 결과 캐시와 같은 방식으로 30초 보관한다.
- 수집기 요청 간격·상한과는 관계없다. 이 요청은 사이트 자체 DB만 읽는다.

### Worker API·Sites 게시

- Worker API 변경: 필요하다. 새 엔드포인트와 응답 형식이 생긴다. 기존 `/api/hotels` 응답은 바꾸지 않는다.
- DB 스키마: 1단계는 바꾸지 않는다. 2단계 색인 열은 마이그레이션과 백업 복원 스키마 갱신이 필요하다.
- Sites 게시: 필요하다. 앱과 Worker가 운영 Sites에서 실행되므로 GitHub 병합만으로 사용자에게 보이지 않는다. 수집기 자료는 바뀌지 않으므로 예약 수집에는 영향이 없다.

### 남은 결정

1. 지도 범위 결과와 목록의 관계: 목록도 범위로 좁힐지, 지도만 바꿀지.
2. 휴대폰 지도 화면에서 지점을 눌렀을 때 미리보기 카드를 쓸지, 바로 상세를 열지.
3. 좌표가 없는 숙소(체크인 자료의 약 97%)를 지도 검색에서 어떻게 안내할지. 좌표 보강은 D02 수집 범위다.

## 지도 범위 검색 1단계 구현(PR B)

기록: 2026-10-10T16:55:00Z / 2026-10-11 01:55:00 KST. 작업 브랜치: `claude/u02-map-bounds`. 기준: main `050d6e4`.
위 ‘지도 범위 검색 설계’를 구현했다. 사용자가 “다음 작업 알아서 진행해 줘”라고 했고, 상위 세션이 남은 결정의 기본값을 전달했다.

### 남은 결정과 근거

1. 지도 범위 결과는 지도에만 적용한다. 목록은 기존 검색 결과를 유지한다. 지도 위에 범위 안 수와 범위 밖 수를 표시한다. 근거: 목록의 결과 세션·쪽 넘김·정렬을 바꾸지 않아 기존 동작과 검사가 그대로 유지된다. 좌표가 있는 기록이 적어서(체크인 자료 57/1,655) 목록까지 범위로 좁히면 대부분의 후보가 목록에서도 사라진다.
2. 휴대폰에서 지점을 누르면 기존 지도 미리보기를 쓴다. 불러온 목록에 없는 지점이면 기존 상세 API(`/api/hotels/<id>`)로 숙소를 받아 같은 미리보기에 넣는다. 새 미리보기 형식은 만들지 않았다.
3. 좌표 없는 숙소는 수로 안내한다(‘위치 미확인 N곳’). 좌표를 추정하지 않는다.

### 구현

- `lib/hotel-repository.ts`: 목록과 지도가 같은 조건을 쓰도록 `searchWhere`를 만들었다. `searchHotels`는 이 함수로 범위 조건과 시설·평점·리뷰 조건을 받는다. 생성되는 SQL과 인자 순서는 이전과 같다.
- `mapArea`와 `GET /api/hotels/map?bbox=서경,남위,동경,북위&<기존 조건>`: 응답은 `total`·`inBounds`·`outOfBounds`·`withoutCoordinates`·`limit`과 `points`(최대 500개: `id`·`name`·`lat`·`lng`·선택한 출처 평점) 또는 `cells`(16×16 격자별 개수·평균 위치·구역 경계)다. 범위 경계는 포함한다. 좌표는 `payload`에서 `json_type`이 숫자인 값만 쓴다(클라이언트의 `hasCoordinates`와 같은 규칙). 스키마는 바꾸지 않았다. 잘못된 범위·조건은 400이다. 기존 `/api/hotels` 응답은 바뀌지 않는다.
- `components/use-map-area.ts`: ‘이 지역에서 검색’을 누를 때만 요청한다. 새 요청은 이전 요청을 취소한다. 같은 조건·범위는 30초 동안 메모리 응답을 쓴다(최대 16개). 조건이 바뀌면 범위 결과를 지운다.
- `components/stay-map.tsx`: 사용자가 지도를 움직였을 때만 버튼을 보인다. 결과 맞춤·카드 선택 같은 코드의 이동은 버튼을 띄우지 않는다. 범위 결과가 있으면 지도를 다시 맞추지 않는다. 격자 지점을 누르면 그 구역으로 확대한다. 검색 뒤에도 버튼을 남겨 키보드 포커스가 사라지지 않게 했다.
- `components/hotel-explorer.tsx`: 지도 열의 표시 줄이 범위 결과(이 지역·범위 밖·위치 미확인·조건에 맞는 전체), 격자 안내, 실패 시 오류와 ‘다시 검색’, ‘불러온 목록 위치로 돌아가기’를 보여 준다.
- `scripts/cloud-check.py --full`에 `check-catalog-worker.mjs`와 새 `check-map-area-worker.mjs`를 넣었다. 앞의 인수인계 정정(PR #14)에서 적은 대로 카탈로그 검사는 그동안 CI에서 실행되지 않았다.

## 지도 지점 키보드 접근성(PR #16 3회째 검토 P3 후속)

기록: 2026-10-11T03:40:00Z / 2026-10-11 12:40:00 KST. 작업 브랜치: `claude/u02-map-keyboard`. 기준: main `651ddfb`(PR #17 병합).

### 문제

1. `autoPanOnFocus:false`(PR #16) 뒤로 화면 밖 지점도 Tab 순서에 남았다. 포커스가 가도 지도가 움직이지 않으므로 포커스 표시가 보이지 않았다.
2. Leaflet 1.9.4의 지점 `keypress` 처리는 팝업을 붙인 지점에만 있다(`bindPopup`이 `_onKeyPress`를 붙인다). 이 앱은 팝업을 쓰지 않으므로 지점에서 Enter·Space를 눌러도 아무 일도 없었다. 격자 지점의 확대와 범위 결과 지점의 미리보기를 키보드로 쓸 수 없었다.

### 결정과 구현(`components/stay-map.tsx`, `components/hotel-explorer.tsx`)

- Tab 정지: 지점 상자(52×36px) 전체가 지도 안에 있을 때만 `tabindex=0`, 아니면 `-1`이다. 지도가 움직이거나 확대·축소되면 `moveend`에서 지점을 다시 그리면서 다시 정한다. 창 크기 변화로 지도 크기만 바뀌는 경우는 `resize`에서 다시 정한다. 일부만 보이는 지점도 Tab 순서에서 뺀다. 포커스 테두리가 잘리기 때문이다. 지도 위의 표시 수·확대 버튼 같은 겹친 요소 밑의 지점은 지도 안으로 본다.
- Enter·Space: 지점 요소의 `keydown`에서 클릭과 같은 동작을 한다(키 반복은 무시, 기본 동작은 막아 Space가 페이지를 스크롤하지 않음). 단일 지점은 기존 미리보기를 열고, 겹친 지점은 그 숙소들로 확대하고, 격자 지점은 그 구역으로 확대한다.
- 다시 그릴 때의 포커스: 지점은 `moveend`·선택 변경 때마다 새로 만들어지므로 포커스가 BODY로 떨어질 수 있었다. 다시 그리기 전에 포커스가 지점에 있었으면, 같은 숙소(겹친 지점이면 첫 숙소)나 같은 구역이 든 새 지점으로 옮긴다. 그 지점이 지도 밖이면 지도 자체(`.leaflet-container`, 방향키로 이동 가능)로 옮긴다. 그래서 겹친 지점·격자 지점을 키보드로 열면 확대 뒤에도 포커스가 그 숙소·구역의 지점에 남는다.
- 미리보기: 키보드로 단일 지점을 열면 미리보기가 나타날 때 포커스가 미리보기의 숙소 이름 버튼(상세 열기)으로 간다. 목록에 없는 범위 결과 지점은 상세 API를 받는 동안 포커스가 지점에 남고, 받지 못하면 기존 안내(토스트)가 나오고 포커스는 지점에 남는다. 미리보기의 닫기 버튼을 누르면 포커스가 그 숙소가 든 지점으로 돌아온다. 마우스·터치로 연 미리보기는 포커스를 옮기지 않는다(기존 동작).
- PR #16의 두 조건은 유지한다. 지점에 `autoPanOnFocus:false`가 그대로 있고, 앞으로 Tab하면 BODY를 거치지 않고 ‘이 지역에서 검색’ 버튼에 닿는다.
