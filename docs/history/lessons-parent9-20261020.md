## 1. 바쁜 하위 세션에 보낸 지시는 그 세션의 턴이 끝난 뒤에야 닿는다

- 있었던 일(10-19): 상위 세션이 18:19:53Z에 하위 세션 L01에게 ‘우리 숙소와 이어지지 않은 간이숙소·하숙 행은 공개 저장소에 커밋하지 말라’는 지시를 보냈다. L01은 그 메시지를 18:57:49Z에야 읽었다. 그 사이 18:56Z에 걸러내기 전 1,973행이 든 PR을 열었다. 그 뒤 ‘force-push하지 말고 squash로 병합한다’는 두 번째 지시도 L01이 이미 force-push한 뒤(19:19Z)에 닿았다(19:42:59Z 읽음). 두 번 모두 메시지가 엇갈렸다.
- 까닭: `send_message`는 기본 우선순위로 보내면 받는 세션의 지금 턴이 끝난 뒤에 처리된다. 도구에는 `priority`(`now`는 지금 턴을 끊음, `next`는 지금 턴에 합류, `later`는 턴이 끝난 뒤)가 있는데, 상위 세션이 쓰지 않았다.
- 교훈 후보(`child-session-orchestration`): push나 PR 열기 전에 반드시 지켜야 하는 제약을 바쁜 하위 세션에 보낼 때는 `priority` `next`(또는 급하면 `now`)로 보내고, 받았다는 답을 받은 뒤에 그 하위 세션이 push하게 한다. brief에는 ‘push하기 전에 들어온 메시지를 먼저 읽는다’를 넣는다.
- 손실 처리: 공개 PR 브랜치에 이미 올라간 커밋은 force-push해도 PR 타임라인으로 계속 열린다. 상위 세션은 그 PR을 squash로 병합해 main 이력에는 걸러낸 결과만 들어가게 했다(사용자는 GitHub 지원에 완전 삭제를 요청하지 않기로 함, 10-20). 공개 저장소에서 ‘커밋하면 안 되는 자료’가 PR에 먼저 들어간 경우의 기본 처리로 쓸 만하다.

## 2. 자동 검사의 판정을 예상해 보고하기 전에 그 검사의 코드를 읽는다

- 있었던 일(10-20T01:23Z): 상위 세션이 ‘0쪽 수집 실행 때문에 오늘 매일 점검이 실패 메일을 보낼 것’이라고 사용자에게 보고하고 기록 PR로 병합했다. 하위 세션 O03이 2분 뒤 코드(`daily-check.mjs`의 `runFailures`: 0쪽 실행은 쓰기·읽기 예산이 둘 다 남았을 때만 실패)를 들어 바로잡았다. 상위 세션은 기록을 고친 PR을 하나 더 냈다.
- 교훈 후보(전역 룰 3절 근처나 `deep-review`): 검사가 무엇을 실패로 볼지 예상해서 적거나 보고하기 전에, 그 판정 조건을 코드나 설정에서 직접 읽는다. 문서의 요약 문장(여기서는 ‘0쪽 실행이면 실패’)은 그 뒤에 더해진 예외를 담지 못할 수 있다.

## 4. GitHub Actions의 `schedule` 이벤트는 10월 초부터 대부분 오지 않는다

- 잰 것(10-20T04:3xZ, 비공개 실행기 저장소의 예약 실행 목록): 수집 예약은 10-14부터 10-19까지 날마다 5번만 왔다. cron이 3시간마다(하루 8칸)일 때와 매시간(하루 24칸)일 때가 같다. 하루 한 번 예약 둘은 2–5시간 늦게 오거나 오지 않았다. 온 실행은 모두 성공했다.
- 바깥 자료(10-20 읽음): GitHub 문서 `docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows`의 schedule 절은 ‘If the load is sufficiently high enough, some queued jobs may be dropped.’라고 하고, 권하는 조치는 정각을 피하는 것뿐이다. 커뮤니티 글 `github.com/orgs/community/discussions/209507`(10-04 시작)에 같은 증상이 이어지며, 10-19 글은 ‘only 13 runs across 192 nominal slots’이다. GitHub 직원 답은 없다. githubstatus 사고는 그 기간 10-19의 67분 한 건뿐이다.
- 교훈 후보(`cloud-session-ops` 또는 Actions를 다루는 스킬): 반드시 돌아야 하는 일을 `schedule`에만 맡기지 않는다. cron 분을 바꿔도 늘지 않는다. 대신 `workflow_dispatch` 사슬(공개 저장소면 기다리는 시간에 Actions 분 비용이 없음)이나 바깥 예약기(Cloudflare Workers Free의 Cron Trigger, 계정당 5개)로 부르고, 예약이 실제로 몇 번 왔는지 잰다.
