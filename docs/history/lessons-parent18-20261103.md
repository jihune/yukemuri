## 1. 일하는 하위 세션의 기록 커밋을 상위 세션 기록 PR로 가져오다 부딪힘

- 일어난 일: 인계 1의 4(“main에 없는 기록 커밋은 다음 기록 PR에 가져온다”)대로 O03 브랜치의 기록 커밋 둘을 상위 세션의 기록 PR #283에 cherry-pick했다. 같은 시각 O03은 그 둘과 뒤 기록을 담은 자기 기록 PR #281을 열었다. 같은 줄을 두 PR이 고치게 되어, 상위 세션 브랜치에서 그 둘을 rebase로 빼고 강제 push하려 했으나 자동 권한 검사가 ‘Git Destructive’로 막았다. 원격 브랜치를 merge로 합친 뒤 `git revert`로 빼서 순변화 0으로 병합했다.
- 교훈: 하위 세션이 일하는 중(running이거나 예약이 막 불린 때)이면 그 브랜치의 기록 커밋을 가져오기 전에 그 세션이 자기 기록 PR을 낼지 먼저 묻는다. 자기 브랜치라도 이미 push한 이력을 다시 쓰는 길은 자동 권한 검사가 막으니, 처음부터 merge와 revert로 고칠 수 있게 커밋을 나눠 둔다.
- 하네스에 제안: `child-session-orchestration`의 기록 줄 가져오기 항목에 ‘일하는 하위 세션이면 먼저 물음’ 한 줄.

## 2. 사용자가 다른 세션에 넣으려던 글을 이 세션에 넣었을 때 넓게 퍼뜨리려 함

- 일어난 일: 사용자가 하네스 관리 세션에 넣으려던 ‘5시간 세션 사용량 관련 … (local claude code 포함) 미리 클라우드에 띄워져 있는 세션들에는 메시지로 알리거나 하자’를 이 세션에 넣었다. 상위 세션은 이것을 계정 전체 일로 읽고 하네스 관리 세션과 다른 프로젝트 세션에 보내려다 사용자가 도구 호출을 거절했다. 사용자가 곧 ‘유케무리 관련 세션들에게만 전파’로 고쳤다.
- 교훈: 프로젝트 세션에 온 글이 다른 프로젝트, 로컬 PC, 하네스 같은 계정 전체를 말하면 받을 곳을 먼저 한 줄로 확인한다. 확인 전에는 자기 프로젝트 범위로만 한다. 오래 쉬는 세션을 메시지로 깨우면 그 세션이 맥락을 다시 읽어 사용량이 드니, 깨울 범위를 넓힐 때는 그 비용을 함께 적는다.

## 4. 미리 적은 판정이 기준값 때문에 ERROR일 때

- 일어난 일: C07이 Jalan 욕장 받기 질의를 재며 판정 규칙을 실행 전에 커밋했는데, 맞춤 기준으로 다른 방법의 값(1,199행)을 골라 R0가 `ERROR`였다. 측정 뒤 운영 13번 대조(0.91–1.15배)가 원인을 강하게 가리켰다. 상위 세션은 판정을 다시 읽지 않고, 고치는 PR 안에서 고치기 전후를 새로 미리 적은 규칙으로 재는 것을 사용자 결정 ‘확인되면 고침’의 확인으로 삼았다. 시도 3이 그 규칙을 모두 통과했다.
- 교훈: 미리 적은 판정이 맞춤 단계에서 실패하면 결과를 보고 판정을 고쳐 쓰지 않는다. 다음 단계의 판정을 새로 미리 적고 그것을 확인으로 삼는다. 맞춤 기준은 같은 도구로 잰 앞 값(이번에는 10-19의 3,022행)을 쓴다.
- 하네스에 제안: `counting-discipline` 「Write the verdict rule before the run」에 ‘맞춤 기준은 같은 도구의 앞 측정에서 고른다, 맞춤이 ERROR면 다음 단계의 미리 적은 판정으로 확인한다’ 한 줄.
