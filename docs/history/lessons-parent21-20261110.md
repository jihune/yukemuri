# 스물한 번째 상위 세션의 교훈(2026-11-10)

유케무리 스물한 번째 상위 세션 `session_01Up3F22x1d1f7nB2PqFvRQu`이 2026-11-10T11:47Z 뒤에 적었다. 하네스 관리 세션에 보낼 것만 모았다. 경위는 `docs/work-handoff-latest.md` 「상위 세션 인계」 7·8에 있다.

1. 사용량을 `list_events(kinds=["rate_limit_event"], limit=100)`의 마지막 이벤트로 읽으면, 세션이 길어진 뒤에는 빈 결과가 온다. `kinds`는 쪽을 읽은 뒤에 거르므로, 가장 새 100개 이벤트에 `rate_limit_event`가 하나도 없으면 `data` 없이 `has_more` true만 온다(이 세션 06:07:40Z에는 0.47을 읽었고, 06:25Z에 같은 호출은 빈 쪽이었다). `get_session`의 `rate_limit_info`에는 `status`와 `resetsAt`만 있고 utilization이 없다. 하네스 후보: `cloud-usage-limits`의 읽는 법에 ‘빈 쪽이면 `before_id`로 거슬러 첫 `rate_limit_event`를 찾는다’를 더함.
2. 받는 쪽 누락 점검(`user_messages.py extract`)이 보내는 쪽 대조가 놓친 시각 하나를 찾았다. 스무 번째는 ‘원래도 sonnet 세션 위주로 …’를 ‘05:30:41Z 뒤’에 쓴 글로 적었지만 이벤트 시각은 05:29:36Z, 곧 질문 답보다 앞이었다. 보내는 쪽은 자기 대화 기록에서 글을 뽑아 `grep -c -F`로 있는지만 보았고 시각은 기억으로 적었다. 하네스 후보: `session-handoff`의 보내는 쪽 대조에서 시각은 뽑은 출력의 `at` 값을 옮겨 적는다.
3. `create_session`으로 연 상위 세션(자동 모드)에서 실행기 저장소 `add_repo`(push)가 이번에는 자동 권한 검사에 막히지 않았다(11-10T06:08Z). 열다섯–열아홉 번째는 모두 처음에 막혀 사용자의 승인 문장이 필요했다. 무엇이 달라졌는지는 확인하지 못했다(추정: 분류기나 정책 변경). 하네스 후보는 없고, 같은 일이 되풀이되는지 다음 인계에서 본다.
4. 인계 1의 6(‘모든 하위 세션에 새 id를 알린다’)이 쉬는 세션 알림에 관한 사용자 결정(11-10T00:59:45Z ‘다음 일 때 알림’)과 부딪혔다. 이번에는 일하는 하위 세션 다섯도 모두 캐시가 식은 대기 상태라, 사용자 결정을 따라 다음 병합 알림 예약에 새 id를 실었다. V01은 09:23Z 자기 안전망 예약 때 스스로 새 id를 찾아 자기 예약 넷을 고쳤다. setup 62의 `cloud-session-renewal`(쉬는 하위 세션에는 따로 보내지 않음)이 같은 결론이라 하네스 후보는 없다.
