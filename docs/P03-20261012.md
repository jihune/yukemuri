## 목표와 PR 나눔

목록·검색·지도(검색 색인·추천 포함)는 Worker를 호출하지 않는다. GitHub Actions가 D1에서 검색용 스냅숏을 만들어 Worker 정적 자산으로 배포하고, 브라우저가 필터·정렬·쪽·지도·이름 부분일치·오타 색인을 계산한다. Worker에는 요청당 읽기가 작은 API만 남긴다.

| PR | 범위 |
|---|---|
| A | 스냅숏 형식·생성기(로컬 SQLite·원격 D1)·배포 경로(`deploy.yml`)·검사·측정 |
| B | 브라우저 검색으로 화면 전환, 첫 화면 정적 HTML, 서버 목록·검색·지도 경로 제거, 응답 비교·브라우저 검사 |
| C | 공개 집계 API 정리(`/api/collection-status`·`/api/photo-credits`), 경로별 D1 읽기 상한·CPU 측정, 읽기 요청의 D1 쓰기 제거 |

main은 각 PR 병합 뒤에도 배포할 수 있어야 한다. A만 병합되면 배포가 스냅숏을 함께 올리지만 화면은 아직 쓰지 않는다.

## Cloudflare 정적 자산(문서 원문, 2026-10-11 확인)

`developers.cloudflare.com`은 이 환경에서 막혀(프록시 거절) 문서 원본 레포 `cloudflare/cloudflare-docs` production `0d35c2c`를 직접 읽었다.

- `workers/static-assets/billing-and-limitations.mdx`: “Requests to static assets are free and unlimited. Requests to the Worker script (for example, in the case of SSR content) are billed according to Workers pricing.” `run_worker_first`에 걸린 경로는 Worker를 부른다. 이 레포는 `run_worker_first`를 쓰지 않는다(생성된 `wrangler.json`의 `assets`는 `{"directory":"../client"}`뿐).
- `workers/platform/limits.mdx` ‘Static Assets’: Workers Free는 Worker 버전당 파일 20,000개, 파일 하나 25 MiB. `_headers` 규칙 100개.
- `workers/static-assets/routing/worker-script.mdx`: 정적 자산과 Worker가 함께 있으면 맞는 자산을 먼저 내보내고, 없을 때만 Worker를 부른다.
- `workers/static-assets/headers.mdx`: 기본 `Cache-Control: public, max-age=0, must-revalidate`와 `ETag`. `_headers`로 바꿀 수 있다.
- 압축(gzip·brotli) 전송 여부는 원문에서 확인하지 못했다(미확인). 첫 배포 뒤 응답 헤더로 확인한다.

## A. 스냅숏 생성기와 배포 경로

### 형식(`lib/search-snapshot.ts`)

- `/snapshot/manifest.json`: 형식 번호 1, 내용 해시 id, 생성 시각, 숙소 수, coverage(목록 화면의 수집 집계), 파일 경로와 크기. 기본 헤더(매번 재검증)로 나간다.
- `/snapshot/v/<id>/core.json`: 검색 열. 숙소 id 순(SQLite BINARY)의 열별 배열이다. 값은 지금 SQL이 거르고 정렬하던 `hotels` 표의 열(지역·도도부현·이름·종류·Trip/Jalan 점수와 리뷰 수·천연·시설 비트·확인 비트)과 생애주기 상태, 좌표(지도 질의와 같은 규칙: 위도·경도가 둘 다 JSON 숫자일 때만)다.
- `cards.json`: 목록 카드·지도 표지·지도 미리보기가 쓰는 필드(`HotelSummary`). 서버 목록과 같은 순서로 만든다: `enrichHotel` → 출처 묶음(`attachSourceGroups`) → 생애주기(`attachLifecycle`). 값이 없는 시설 사실과 모의 평점은 화면에서 없는 것과 같아 뺐다. 상세는 지금처럼 `/api/hotels/<id>`가 준다.
- `text.json`: 이름 검색. 부분일치용 `search_text`·`hotel_names.name_key`, 오타 색인용 이름·위치·지명 문맥(폐업·휴관은 지금 색인처럼 null).
- `status.json`: 수집 현황(지금 `/api/collection-status`와 같은 값, 시각은 생성 시각).
- `_headers`에 `/snapshot/v/*`를 `public, max-age=31536000, immutable`로 더한다. 버전 폴더는 하나만 둔다(파일 4개).

### 생성기(`scripts/build-search-snapshot.mjs`, `lib/search-snapshot-build.ts`)

- lib/를 tsc로 Node용 CommonJS로 컴파일해 Worker와 같은 함수로 만든다(P02 #38의 `bench-search-cpu.mjs` 방식). `cloudflare:workers`는 생성기가 준 env로 바꾼다.
- 원본: `--sqlite <파일>`(node:sqlite 읽기 전용) 또는 `--remote`(Cloudflare API `POST /accounts/{account}/d1/database/{id}/query`, `cloudflare/api-schemas` main `3fad73e`의 `d1_batch-query`: params는 문자열). 토큰·계정은 환경 변수 `CLOUDFLARE_API_TOKEN`·`CLOUDFLARE_ACCOUNT_ID`, DB id는 `cloudflare-deploy.json`. 429·5xx는 세 번까지 다시 보낸다. 오류 문구에 토큰·계정을 넣지 않는다.
- 읽기 전용: `SELECT`·`WITH`로 시작하는 한 문장만 보낸다. 그 밖의 문장과 `run()`은 보내기 전에 거절한다.
- 출처 묶음·생애주기 조회는 그 행이 있는 숙소에만 한다. 처음 판(모든 숙소를 id로 조회)은 운영 규모 복사본에서 생성 1회 읽기 197,002행이었고, 바꾼 뒤 103,844행이다. 묶음 없는 숙소는 `composePreferredHotel(h,[])`(지금 `attachSourceGroups`가 그 숙소에 하는 일), 생애주기 행 없는 숙소는 그대로다. 검사가 모든 숙소의 카드를 Worker 응답과 대조한다.

### 배포 경로

- `deploy.yml`: `cloud-check.py --full` → time travel 복구 지점 → `migrations apply` → **스냅숏 생성(`--remote`)** → `deploy` → smoke. 생성은 마이그레이션 뒤라 새 스키마를 읽는다. 크기·읽기 행 수를 실행 요약에 남긴다.
- 갱신 시점: main push 배포 때, 수동 실행 때, 그리고 `workflow_call`. 6단계 수집 workflow가 수집 실행 끝에 `uses: ./.github/workflows/deploy.yml`(`secrets: inherit`)로 부르면 스냅숏이 수집을 따라간다. 같은 동시 실행 그룹(`cloudflare-account`)이라 배포와 겹치지 않는다. 이 경로는 그때의 main을 다시 검사·배포한다. main은 push마다 이미 자동 배포되므로 코드가 바뀌지는 않는다.
- `d1-setup.yml`은 바꾸지 않았다. 스냅숏은 Worker 배포와 함께 올라가는 자산이라 D1만 만드는 workflow와 관계없다.
- `cloudflare-smoke.mjs`: `/snapshot/manifest.json`이 200이고 이번 실행이 만든 id인지, 파일 네 개가 200인지 본다.

### 측정(운영 규모 복사본, `docs/evidence/p03-snapshot-grown-20261012.json`)

`node scripts/measure-search-snapshot.mjs --grow`: 체크인 자료를 2026-10-08 행 수(숙소 12,271, 이름 13,849, 대기열 15,417, 생애주기 1,621)로 복사해 늘린 임시 D1.

- D1 읽기: 생성 1회 103,844행(66개 질의, Miniflare `rows_read` 합). 큰 몫은 수집 현황·집계의 `crawl_jobs` 전체 집계 3회(약 5만 행)와 `hotels`·`hotel_names` 읽기다. 하루 8회면 약 83만 행, 실제 실행 빈도(하루 약 3회)면 약 31만 행이다. 무료 한도 하루 500만 행 안이다. 쓰기는 0행이다.
- 크기(복사본은 반복 때문에 압축이 지나치게 잘 된다. 그래서 체크인 규모의 압축 크기에 행 비율 7.41을 곱한 추정을 같이 쓴다):

| core | 1,736KiB | 305KiB | 235KiB | 첫 방문 |

- 브라우저 해석 시간·메모리는 PR B에서 휴대폰 수준 CPU 제한으로 잰다.

### 검사

- 새 `scripts/check-search-snapshot-worker.mjs`(공통 검사에 추가): 빌드한 Worker와 임시 D1에서 수집 준비(`/api/crawl-prepare`)로 채우고, 생애주기·별칭·문자열 좌표·저장 이름이 다른 큐레이션 숙소를 더한 뒤 생성한다. 단언: core 열이 표와 같음, text가 표와 지금 `/api/hotels/search-index`와 같음(폐업·휴관 제외 포함), 카드 1,655개가 `/api/hotel-comparison`이 준 숙소의 카드 필드와 같음, coverage가 `/api/hotels`의 값과 같음, status가 `/api/collection-status`와 같음, 생성 전후 D1 표가 같음(쓰기 없음), 읽기 전용 가드가 쓰기 문장 5종과 `run()`을 거절함, 가짜 Cloudflare API 원본이 같은 스냅숏(같은 id)을 만들고 문자열 params·429 재시도·토큰 없는 오류, 다시 만들면 같은 id·버전 폴더 하나·`_headers` 규칙 한 번.
- 대조 변형(각각 검사 실패 확인): 생애주기 붙이기 제거, 좌표 숫자 규칙 제거, 읽기 전용 가드 제거, 색인 이름을 저장값 대신 정제된 이름으로. 처음 넣은 변형 ‘지명 문맥을 정제된 숙소로’는 체크인 자료에서 값이 같아 통과했다. 그래서 큐레이션 숙소의 저장 이름을 바꾸는 준비를 더했고, 이름 변형이 실패하는 것을 확인했다.
- `check-deploy-config.mjs`: 배포 순서에 스냅숏 단계, `workflow_call` 단언을 더했다.

### 미확인(A)

- 실제 Cloudflare API의 `/query` 응답 형식과 결과 크기 한도. 생성기는 500곳씩 읽는다(한 응답 약 1–2MB). 첫 실제 배포에서 확인한다(상위 세션).
- 정적 자산의 압축 전송, `_headers` 규칙 적용. 첫 배포 뒤 응답 헤더로 확인한다.
- 사용자 토큰의 D1 권한으로 `/query` 읽기가 되는지. 3단계에서 같은 토큰으로 D1 생성·마이그레이션이 됐으므로 될 것으로 보지만 실행 전까지 미확인이다.
