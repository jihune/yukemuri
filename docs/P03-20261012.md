## 목표와 PR 나눔

목록·검색·지도(검색 색인·추천 포함)는 Worker를 호출하지 않는다. GitHub Actions가 D1에서 검색용 스냅숏을 만들어 Worker 정적 자산으로 배포하고, 브라우저가 필터·정렬·쪽·지도·이름 부분일치·오타 색인을 계산한다. Worker에는 요청당 읽기가 작은 API만 남긴다.

| PR | 범위 |
|---|---|
| A | 스냅숏 형식·생성기(로컬 SQLite·원격 D1)·배포 경로(`deploy.yml`)·검사·측정 |
| B | 브라우저 검색으로 화면 전환, 첫 화면 정적 HTML, 서버 목록·검색·지도 경로 제거, 응답 비교·브라우저 검사 |
| C | 공개 집계 API 정리(`/api/collection-status`·`/api/photo-credits`), 경로별 D1 읽기 상한·CPU 측정, 읽기 요청의 D1 쓰기 제거 |

main은 각 PR 병합 뒤에도 배포할 수 있어야 한다. A만 병합되면 배포가 스냅숏을 함께 올리지만 화면은 아직 쓰지 않는다.

## A. 스냅숏 생성기와 배포 경로

### 형식(`lib/search-snapshot.ts`)

- `/snapshot/manifest.json`: 형식 번호 1, 내용 해시 id, 생성 시각, 숙소 수, coverage(목록 화면의 수집 집계), 파일 경로와 크기. 기본 헤더(매번 재검증)로 나간다.
- `/snapshot/v/<id>/core.json`: 검색 열. 숙소 id 순(SQLite BINARY)의 열별 배열이다. 값은 지금 SQL이 거르고 정렬하던 `hotels` 표의 열(지역·도도부현·이름·종류·Trip/Jalan 점수와 리뷰 수·천연·시설 비트·확인 비트)과 생애주기 상태, 좌표(지도 질의와 같은 규칙: 위도·경도가 둘 다 JSON 숫자일 때만)다.
- `cards.json`: 목록 카드·지도 표지·지도 미리보기가 쓰는 필드(`HotelSummary`). 서버 목록과 같은 순서로 만든다: `enrichHotel` → 출처 묶음(`attachSourceGroups`) → 생애주기(`attachLifecycle`). 값이 없는 시설 사실과 모의 평점은 화면에서 없는 것과 같아 뺐다. 상세는 지금처럼 `/api/hotels/<id>`가 준다.
- `text.json`: 이름 검색. 부분일치용 `search_text`·`hotel_names.name_key`, 오타 색인용 이름·위치·지명 문맥(폐업·휴관은 지금 색인처럼 null).
- `status.json`: 수집 현황(지금 `/api/collection-status`와 같은 값, 시각은 생성 시각).
- `_headers`에 `/snapshot/v/*`를 `public, max-age=31536000, immutable`로 더한다. 버전 폴더는 하나만 둔다(파일 4개).

### 생성기(`scripts/build-search-snapshot.mjs`, `lib/search-snapshot-build.ts`)

- lib/를 tsc로 Node용 CommonJS로 컴파일해 Worker와 같은 함수로 만든다(P02 #38의 `bench-search-cpu.mjs` 방식). `cloudflare:workers`는 생성기가 준 env로 바꾼다.
- 원본: `--sqlite <파일>`(node:sqlite 읽기 전용) 또는 `--remote`(Cloudflare API `POST /accounts/{account}/d1/database/{id}/query`, `cloudflare/api-schemas` main `3fad73e`의 `d1_batch-query`: params는 문자열). 토큰·계정은 환경 변수 `CLOUDFLARE_API_TOKEN`·`CLOUDFLARE_ACCOUNT_ID`, DB id는 `cloudflare-deploy.json`. 429·5xx는 세 번까지 다시 보낸다. 오류 문구에 토큰·계정을 넣지 않는다.
- 읽기 전용: `SELECT`·`WITH`로 시작하는 한 문장이고, 문자열·주석 밖 어디에도 쓰기 단어(`INSERT`·`UPDATE`·`DELETE`·`REPLACE`·`RETURNING`·`PRAGMA` 등)가 없을 때만 보낸다. 그 밖의 문장과 `run()`은 보내기 전에 거절한다. CTE 뒤의 쓰기(`WITH x AS (...) DELETE ...`)도 거절한다(Codex 검토 P2, 아래).
- 출처 묶음·생애주기 조회는 그 행이 있는 숙소에만 한다. 처음 판(모든 숙소를 id로 조회)은 운영 규모 복사본에서 생성 1회 읽기 197,002행이었고, 바꾼 뒤 103,844행이다. 묶음 없는 숙소는 `composePreferredHotel(h,[])`(지금 `attachSourceGroups`가 그 숙소에 하는 일), 생애주기 행 없는 숙소는 그대로다. 검사가 모든 숙소의 카드를 Worker 응답과 대조한다.

### 배포 경로

- `deploy.yml`: `cloud-check.py --full` → time travel 복구 지점 → `migrations apply` → **스냅숏 생성(`--remote`)** → `deploy` → smoke. 생성은 마이그레이션 뒤라 새 스키마를 읽는다. 크기·읽기 행 수를 실행 요약에 남긴다.
- 쓰기와 겹치지 않게: 생성은 D1을 여러 요청으로 읽어 하나의 시점이 아니다. 그래서 배포는 수집과 같은 동시 실행 그룹(`yukemuri-catalog-updates`)에서 기다린다. 잠금은 둘이고 언제나 같은 순서로 잡는다. 바깥은 workflow 최상위의 카탈로그 그룹, 안쪽은 배포 job의 계정 그룹(`cloudflare-account`, `d1-setup.yml`과 공유)이다. 수집 workflow가 끝에 부를 때(`after_collection: true`)는 수집이 이미 카탈로그 그룹을 쥐고 있다. 그래서 최상위는 별도 그룹(`yukemuri-snapshot-after-collection`)을 쓰고(같은 그룹이면 호출한 수집을 기다린다), 그 안에서 계정 그룹을 잡는다. 6단계 수집 workflow는 최상위 그룹을 `yukemuri-catalog-updates`로 두고 `with: {after_collection: true}`로 불러야 하며, 계정 그룹을 먼저 잡지 않아야 한다. 4단계 적재(실행기 레포)는 이 그룹 밖이지만 적재가 끝난 뒤에 `autoDeploy`를 켠다. 같은 그룹의 대기 실행은 하나뿐이라, 배포가 겹치면 대기 중인 수집 실행이 취소될 수 있다(실행기 예약의 다음 실행과 12시간 감시가 남는다).
- 갱신 시점: main push 배포 때, 수동 실행 때, 그리고 `workflow_call`. 6단계 수집 workflow가 수집 실행 끝에 `uses: ./.github/workflows/deploy.yml`(`secrets: inherit`)로 부르면 스냅숏이 수집을 따라간다. 이 실행도 계정 그룹을 잡으므로 다른 배포와 겹치지 않는다. 이 경로는 그때의 main을 다시 검사·배포한다. main은 push마다 이미 자동 배포되므로 코드가 바뀌지는 않는다.
- `d1-setup.yml`은 바꾸지 않았다. 스냅숏은 Worker 배포와 함께 올라가는 자산이라 D1만 만드는 workflow와 관계없다.
- `cloudflare-smoke.mjs`: `/snapshot/manifest.json`이 200이고 이번 실행이 만든 id인지, 파일 네 개가 200인지 본다.
