## 목표와 PR 나눔

목록·검색·지도(검색 색인·추천 포함)는 Worker를 호출하지 않는다. GitHub Actions가 D1에서 검색용 스냅숏을 만들어 Worker 정적 자산으로 배포하고, 브라우저가 필터·정렬·쪽·지도·이름 부분일치·오타 색인을 계산한다. Worker에는 요청당 읽기가 작은 API만 남긴다.

| PR | 범위 |
|---|---|
| A | 스냅숏 형식·생성기(로컬 SQLite·원격 D1)·배포 경로(`deploy.yml`)·검사·측정 |
| B | 브라우저 검색으로 화면 전환, 첫 화면 정적 HTML, 서버 목록·검색·지도 경로 제거, 응답 비교·브라우저 검사 |
| C | 공개 집계 API 정리(`/api/collection-status`·`/api/photo-credits`), 경로별 D1 읽기 상한·CPU 측정, 읽기 요청의 D1 쓰기 제거 |

main은 각 PR 병합 뒤에도 배포할 수 있어야 한다. A만 병합되면 배포가 스냅숏을 함께 올리지만 화면은 아직 쓰지 않는다.

## A. 스냅숏 생성기와 배포 경로

### 형식(`lib/search-snapshot.ts`)

- `/snapshot/manifest.json`: 형식 번호 1, 내용 해시 id, 생성 시각, 숙소 수, coverage(목록 화면의 수집 집계), 파일 경로와 크기. 기본 헤더(매번 재검증)로 나간다.
- `/snapshot/v/<id>/core.json`: 검색 열. 숙소 id 순(SQLite BINARY)의 열별 배열이다. 값은 지금 SQL이 거르고 정렬하던 `hotels` 표의 열(지역·도도부현·이름·종류·Trip/Jalan 점수와 리뷰 수·천연·시설 비트·확인 비트)과 생애주기 상태, 좌표(지도 질의와 같은 규칙: 위도·경도가 둘 다 JSON 숫자일 때만)다.
- `cards.json`: 목록 카드·지도 표지·지도 미리보기가 쓰는 필드(`HotelSummary`). 서버 목록과 같은 순서로 만든다: `enrichHotel` → 출처 묶음(`attachSourceGroups`) → 생애주기(`attachLifecycle`). 값이 없는 시설 사실과 모의 평점은 화면에서 없는 것과 같아 뺐다. 상세는 지금처럼 `/api/hotels/<id>`가 준다.
- `text.json`: 이름 검색. 부분일치용 `search_text`·`hotel_names.name_key`, 오타 색인용 이름·위치·지명 문맥(폐업·휴관은 지금 색인처럼 null).
- `status.json`: 수집 현황(지금 `/api/collection-status`와 같은 값, 시각은 생성 시각).
- `_headers`에 `/snapshot/v/*`를 `public, max-age=31536000, immutable`로 더한다. 버전 폴더는 하나만 둔다(파일 4개).

### 생성기(`scripts/build-search-snapshot.mjs`, `lib/search-snapshot-build.ts`)

- lib/를 tsc로 Node용 CommonJS로 컴파일해 Worker와 같은 함수로 만든다(P02 #38의 `bench-search-cpu.mjs` 방식). `cloudflare:workers`는 생성기가 준 env로 바꾼다.
- 원본: `--sqlite <파일>`(node:sqlite 읽기 전용) 또는 `--remote`(Cloudflare API `POST /accounts/{account}/d1/database/{id}/query`, `cloudflare/api-schemas` main `3fad73e`의 `d1_batch-query`: params는 문자열). 토큰·계정은 환경 변수 `CLOUDFLARE_API_TOKEN`·`CLOUDFLARE_ACCOUNT_ID`, DB id는 `cloudflare-deploy.json`. 429·5xx는 세 번까지 다시 보낸다. 기다리는 시간은 2·4·8초이고, API가 `Retry-After`(초 또는 HTTP 날짜)로 더 길게 요구하면 그만큼 기다린다. 요구가 5분을 넘으면 기다리지 않고 바로 실패한다(Codex 3회째 P2). 오류 문구에 토큰·계정을 넣지 않는다.
- 읽기 전용: `SELECT`·`WITH`로 시작하는 한 문장이고, 문자열·주석 밖 어디에도 쓰기 단어(`INSERT`·`UPDATE`·`DELETE`·`REPLACE`·`RETURNING`·`PRAGMA` 등)가 없을 때만 보낸다. 그 밖의 문장과 `run()`은 보내기 전에 거절한다. CTE 뒤의 쓰기(`WITH x AS (...) DELETE ...`)도 거절한다(Codex 검토 P2, 아래).
- 출처 묶음·생애주기 조회는 그 행이 있는 숙소에만 한다. 처음 판(모든 숙소를 id로 조회)은 운영 규모 복사본에서 생성 1회 읽기 197,002행이었고, 바꾼 뒤 103,844행이다. 묶음 없는 숙소는 `composePreferredHotel(h,[])`(지금 `attachSourceGroups`가 그 숙소에 하는 일), 생애주기 행 없는 숙소는 그대로다. 검사가 모든 숙소의 카드를 Worker 응답과 대조한다.

### 배포 경로

- `deploy.yml`: `cloud-check.py --full` → time travel 복구 지점 → `migrations apply` → **스냅숏 생성(`--remote`)** → `deploy` → smoke. 생성은 마이그레이션 뒤라 새 스키마를 읽는다. 크기·읽기 행 수를 실행 요약에 남긴다.
- 쓰기와 겹치지 않게: 생성은 D1을 여러 요청으로 읽어 하나의 시점이 아니다. 그래서 배포는 수집과 같은 동시 실행 그룹(`yukemuri-catalog-updates`)에서 기다린다. 잠금은 둘이고 언제나 같은 순서로 잡는다. 바깥은 workflow 최상위의 카탈로그 그룹, 안쪽은 배포 job의 계정 그룹(`cloudflare-account`, `d1-setup.yml`과 공유)이다. 수집 workflow가 끝에 부를 때(`after_collection: true`)는 수집이 이미 카탈로그 그룹을 쥐고 있다. 그래서 최상위는 별도 그룹(`yukemuri-snapshot-after-collection`)을 쓰고(같은 그룹이면 호출한 수집을 기다린다), 그 안에서 계정 그룹을 잡는다. 6단계 수집 workflow는 최상위 그룹을 `yukemuri-catalog-updates`로 두고 `with: {after_collection: true}`로 불러야 하며, 계정 그룹을 먼저 잡지 않아야 한다. 4단계 적재(실행기 레포)는 이 그룹 밖이지만 적재가 끝난 뒤에 `autoDeploy`를 켠다. 같은 그룹의 대기 실행은 하나뿐이라, 배포가 겹치면 대기 중인 수집 실행이 취소될 수 있다(실행기 예약의 다음 실행과 12시간 감시가 남는다).
- 갱신 시점: main push 배포 때, 수동 실행 때, 그리고 `workflow_call`. 6단계 수집 workflow가 수집 실행 끝에 `uses: ./.github/workflows/deploy.yml`(`secrets: inherit`)로 부르면 스냅숏이 수집을 따라간다. 이 실행도 계정 그룹을 잡으므로 다른 배포와 겹치지 않는다. 이 경로는 그때의 main을 다시 검사·배포한다. main은 push마다 이미 자동 배포되므로 코드가 바뀌지는 않는다.
- `d1-setup.yml`은 바꾸지 않았다. 스냅숏은 Worker 배포와 함께 올라가는 자산이라 D1만 만드는 workflow와 관계없다.
- `cloudflare-smoke.mjs`: `/snapshot/manifest.json`이 200이고 이번 실행이 만든 id인지, 파일 네 개가 200인지 본다.

## B. 브라우저 검색으로 화면 전환

### 바뀐 것

- 목록·검색·지도·추천·대안·예상 숙소를 브라우저가 스냅숏에서 계산한다(`lib/static-search.ts`). P02 #38의 순수 함수(정렬·부분일치·오타 색인·지도 격자·SQLite 평균)를 열 배열에 옮겼다. 정렬별 순서는 스냅숏당 한 번 만들어 둔다.
- 스냅숏 읽기: `lib/snapshot-client.ts`, `components/use-search-snapshot.ts`. 첫 방문은 core·cards만 받는다. 이름 검색 파일(text)은 검색어를 입력하거나 예상 숙소·대안이 필요할 때 받는다.
- 서버 경로 제거: `/api/hotels`(목록·검색), `/api/hotels/map`, `/api/hotels/search-index`, `/api/hotels/suggestions`. 결과 세션(`lib/hotel-result-session.ts`·`lib/paged-hotel-results.ts`)과 그 삭제 문장도 뺐다. `hotel_result_sessions` 표는 스키마 변경을 피하려고 남겼다. 이제 쓰는 코드는 없다(삭제 마이그레이션은 상위 세션 판단).
- 첫 화면: `/`는 Worker를 부르지 않는 정적 `index.html`이다(`scripts/build-static-page.mjs`). 스냅숏 단계가 같은 Worker로 페이지를 한 번 더 그리면서, 그 스냅숏의 기본 보기 첫 쪽 40곳을 HTML 카드로 넣는다(`FIRST_PAGE` 바인딩은 빌드 때만 있다). 스냅숏의 manifest도 함께 넣는다. 그래서 첫 방문은 manifest를 따로 받지 않고, core·cards 미리 받기(`preload`, 낮은 우선순위)가 앱 스크립트와 함께 시작된다.
- 조건이 있는 주소(`/?rating=8` 등): 같은 정적 HTML이므로 첫 쪽 카드는 기본 보기의 것이다. head 스크립트는 목록 조건이 기본값과 다를 때 `<html data-conditions>`를 붙인다. 보기(`view`)와 예약 날짜·인원은 목록을 바꾸지 않아 보지 않는다. 앱이 기본값을 모두 적어 둔 주소(`/?region=all&…&sort=recommended&view=split`)는 표시하지 않는다(Codex 검토 1회째). CSS는 앱이 주소를 읽을 때까지 그 목록과 지도 버튼의 숫자를 숨기고, 대신 “주소의 조건을 적용하는 중…”을 보인다(조건 없는 결과를 그 조건의 결과처럼 보이지 않게). 앱이 주소를 읽으면 표시를 지우고 스냅숏으로 그 조건의 결과를 보인다. 검색창·지역 단추는 앱이 주소를 읽기 전까지 기본값으로 보인다.
- 뒤로 가기: vinext 라우터는 popstate에 RSC 요청을 보낸다. 정적 페이지에서는 이것이 전체 새로고침이 되어 비교 시트 등이 닫혔다. head 스크립트가 popstate를 먼저 받아 `yukemuri:popstate`로 넘긴다(`lib/history-events.ts`).
- 배포 smoke(`cloudflare-smoke.mjs`)는 `/api/hotels` 대신 다음을 확인한다: 정적 페이지가 배포된 스냅숏의 첫 쪽을 담는지, core 첫 숙소의 상세가 200인지, manifest와 파일들. B에서 목록 API를 지우면 기존 smoke가 실패하는 것을 찾아 고쳤다.
- 쓰지 않게 된 측정 도구 `measure-map-area.mjs`·`compare-search-builds.mjs`(서버 지도·검색 경로를 재던 것)는 지웠다. 그 기록은 U02·P02 문서와 증거에 남는다.

### 스냅숏과 상세 API가 다를 때, 스냅숏을 받지 못할 때(화면 동작)

| 경우 | 화면 |
|---|---|
| 스냅숏을 받는 중 | 조건 없는 주소는 HTML의 첫 쪽 카드와 수집 집계를 보인다. 조건 있는 주소는 “조건에 맞는 숙소를 찾는 중…”만 보이고 이전 수나 미확인 안내는 숨긴다. ‘더 불러오기’는 스냅숏이 오면 나타난다. |
| manifest·core·cards를 받지 못함(네트워크, 5xx, JSON 아님) | 오류 안내와 ‘다시 시도’. 다시 시도는 manifest부터 새로 읽는다. 조건 없는 주소의 HTML 첫 쪽은 그대로 남는다. |
| 배포가 바뀌어 옛 버전 파일이 404 | manifest를 한 번 다시 받아 새 버전 전체를 읽는다(core·cards와 text 모두). 두 번째도 404면 오류 안내. |
| manifest 형식 번호가 다름(페이지가 배포보다 오래됨) | “사이트가 새 버전으로 바뀌었습니다. 페이지를 다시 열어 주세요.”와 ‘페이지 다시 열기’ 버튼. 목록은 계산하지 않는다. |
| 이름 검색 파일을 받지 못함 | 검색어가 있는 결과에만 오류 안내와 다시 시도. 조건만 있는 목록은 그대로 쓴다. |
| 스냅숏에는 있는데 상세 API가 404(스냅숏 뒤 삭제) | 시트를 닫고 API 문구(“숙소를 찾을 수 없습니다.”)를 알림으로 보인 뒤, manifest를 다시 확인해 새 스냅숏이면 목록을 바꾼다. |
| 상세 값이 카드와 다름(스냅숏 뒤 갱신) | 시트는 언제나 상세 API 응답으로 연다(카드 값으로 먼저 그리지 않는다). 목록 카드는 다음 스냅숏까지 그대로다. |
| 즐겨찾기에 있으나 스냅숏에 없는 숙소 | 저장 목록에서 빠지고, 다음 스냅숏에 들어오면 다시 보인다. 즐겨찾기 자체(D1)는 바뀌지 않는다. |

U02 브라우저 검사가 받는 중, 실패와 다시 시도, 형식 불일치, 상세 404, 스크립트 없는 첫 쪽, 조건 주소의 숨김을 단언한다. 옛 버전 404 재시도는 `snapshot-client` 코드 경로이고, U02의 ‘다시 시도’ 검사가 manifest를 다시 읽는 것을 확인한다.
