# 두 웹 환경에서 이어가기

기록: 2026-10-09. 구독이나 작성 에이전트가 바뀌어도 같은 레포를 사용한다. 앱 레포는 2026-10-11부터 public이다.
호스팅·DB·기존 Python 수집기는 현 위치에 둔다.

## 최초 연결

1. 전체 앱 레포 `jihune/yukemuri`(public)를 선택한다. 기존 실행기는 별도 레포로 유지한다.
2. 사용하는 서비스에서 GitHub 연결을 설정하고 전체 앱 레포에 접근을 허용한다. Work의 연결이 다른 서비스의 연결을 대신하지 않는다.
3. Codex 클라우드 또는 Claude Code 클라우드에서 같은 레포를 선택한다. Node 24와 Python >=3.10을 사용한다.
4. 환경의 설치 단계에서 레포 루트의 `bash scripts/cloud-setup.sh`를 실행한다. 설치 단계에 레포가 없으면 첫 작업에서 같은 명령을 실행한다.
5. 의존성 설치에 필요한 npm 레지스트리 네트워크를 허용한다. 검사에는 운영 Site Secret이나 공급자 사이트 접근이 필요하지 않다.
6. 첫 세션에서 `python3 scripts/cloud-check.py --full`을 실행하고 결과를 기록한다. Work 컨테이너의 검사와 실제 서비스 환경의 첫 검사는 별개다.

설치 스크립트는 Node 자동 설치나 잠금 파일 갱신을 하지 않는다.
pnpm이 다른 버전이면 환경에서 11.25.0을 준비한 뒤 다시 실행한다.
부족한 개발 도구는 Ubuntu 컨테이너 안에 설치한다. 잠금 파일과 제품 의존성은 바꾸지 않는다. 설치한 도구와 버전은 인수인계에 기록한다.
Claude Code 클라우드(Ubuntu 24.04)의 기본 Node는 22.22.0이었다(2026-10-10T11:21:18Z / 20:21:18 KST 기록). `source /opt/nvm/nvm.sh && nvm install 24`로 Node 24를 설치하고 `/opt/nvm/versions/node/<버전>/bin`을 PATH 앞에 둔다.
서비스의 환경 캐시·작업 디렉터리는 첫 세션에서 확인한다.
클라우드 환경 설정 화면은 서비스 변경에 따라 달라질 수 있다.

## 구현과 검토

이 절의 브랜치·인수인계·병합 절차는 작성 담당에게 적용한다. 검토 담당은 `AGENTS.md`의 검토 세션 규칙을 따른다.
main의 기준 커밋을 확인하고 작업 브랜치를 만든다. 서비스의 브랜치 정책을 따른다.
한 에이전트가 구현하고 다른 에이전트는 같은 PR/커밋을 검토한다. 기록 갱신 PR은 `AGENTS.md`의 예외에 따라 검토 없이 병합한다.
현재 분담은 Claude Code 웹이 구현, Codex 웹이 검토다(사용자 결정, 2026-10-10).
Codex가 검토할 수 없으면 그 PR을 구현하지 않은 새 Claude Code 세션이 검토한다. 절차는 아래 ‘Codex 클라우드 환경’ 절의 3번이다(사용자 결정, 2026-10-10T16:28Z / 2026-10-11 01:28 KST). Codex 요청 세 번을 다 쓴 뒤에는 같은 3번의 ‘이어 가는 Claude 검토’를 두 번까지 쓴다(사용자 결정, 2026-10-11T15:56Z / 2026-10-12 00:56 KST).
검사 실패·충돌을 해결하고 인수인계를 갱신한 뒤 main에 반영한다. 병합 조건은 `AGENTS.md`의 ‘작업 시작과 공동 작업’ 절에 있다. 조건을 충족하면 사용자 확인 없이 작성 담당이 병합한다. 상위 세션이 맡긴 작업은 상위 세션이 병합한다.
Sites 배포는 `sites-handoff.md`의 별도 절차다.
서비스별 대화는 자동 공유되지 않는다. 결정·검사·중단 지점을 레포에 기록한다.

## CI와 Actions 사용 시간

기록: 2026-10-11T06:30Z / 2026-10-11 15:30 KST.

- 앱 레포 CI(`checks`)는 PR과 main push에서만 실행한다. 작업 브랜치 push만으로는 실행하지 않는다. 같은 PR에 새 push가 오면 진행 중인 이전 실행을 취소한다. 문서만 바꾸는 변경은 지금처럼 생략한다.
- 앱 레포는 public이다. 사용자가 GitHub 설정에서 바꿨고 2026-10-11T09:30Z에 API로 확인했다(사용자 결정, 2026-10-11T08:25Z / 17:25 KST). 앱 레포 CI 사용 시간은 이제 한도가 없다. 구현 작업을 한 번에 하나로 묶던 제한은 풀었다. public 레포의 표준 GitHub 호스팅 실행기 사용은 무료다. 비밀값 점검(gitleaks, 앱 레포 전체 이력과 `source-assets`의 원래 Git bundle 두 개)에서 0건이었다. 실행기 레포는 DB 백업 artifact가 있어 private으로 둔다.
- private 레포의 GitHub 호스팅 실행기 사용 시간은 계정 단위 월 한도를 함께 쓴다. GitHub Free 개인 계정의 한도는 월 2,000분이다(Pro는 3,000분). 사용자 계정의 플랜과 결제 주기는 미확인이다.
- 한도를 다 쓰면 실행기 레포의 수집 예약과 일일 백업도 그달 남은 기간 동안 멈출 수 있다.
- 실측 근사치: 앱 레포는 2026-10-10T09:30Z부터 10-11T06:09Z까지 77회(push 40회·PR 37회) 약 272분을 썼다. 실행기 레포는 10-06부터 10-11까지 57회 약 136분을 썼다. 실행마다 시작·갱신 시각 차이를 분 단위로 올려 더했다. 실제 과금 분은 사용자가 GitHub 결제 화면에서 확인한다.
- 작성 담당은 로컬 검사를 통과한 뒤 코드와 기록 커밋을 모아 push한다. 열린 PR에 기록 커밋만 따로 여러 번 push하지 않는다. PR의 CI는 PR 전체 변경을 보고 실행 여부를 정하므로 기록만 바꾼 push도 전체 검사를 다시 실행한다.

## 사용량 한도와 중단 대비

기록: 2026-10-12T09:03Z / 2026-10-12 18:03 KST. 사용자 요청이다(2026-10-11T22:16Z 무렵, 주간 사용량 81%에서 멈추고 2026-10-12T09:03Z에 재개한 뒤).

Claude 구독에는 5시간 창과 주간 한도가 있다. Codex 리뷰는 사용자의 ChatGPT 구독 사용량을 쓴다. 한도에 닿으면 세션이 일을 멈춘다. 다만 Claude 유료 플랜에서 사용량 크레딧(추가 사용량)이 켜져 있으면 한도 뒤에도 종량 과금으로 계속 돈다(Claude 도움말 ‘Manage usage credits for paid Claude plans’). 사용자는 추가 결제를 하지 않기로 했으므로 크레딧은 꺼 두는 것을 전제로 한다(켜짐 여부는 사용자가 claude.ai 설정에서 확인한다). 세션 상태의 `isUsingOverage`가 `true`이면 크레딧으로 돌고 있는 것이므로, 상위 세션은 새 작업을 멈추고 체크포인트를 적은 뒤 사용자에게 알린다. 웹 세션은 대화가 남아 이어 갈 수 있다. 하지만 쉬는 동안 컨테이너가 회수되면 push하지 않은 변경과 컨테이너 안에서 돌던 프로그램은 사라진다. 그래서 다음을 지킨다.

1. 의미 있는 단위마다 커밋하고 작업 브랜치에 push한다.
2. 오래 걸리는 작업(적재·배포·긴 측정)은 GitHub Actions에서 돌린다. 컨테이너 안 배경 작업이나 하위 에이전트에 맡긴 결과는 끝나는 대로 파일이나 커밋으로 남긴다.
3. 일부러 멈출 때는 인수인계에 체크포인트를 적는다. 멈춘 시각, 브랜치 head, 끝난 것, 남은 것, 재개 첫 단계, 진행 중인 배경 작업이 없다는 확인이다. 예약(`send_later`)은 재개 예약 하나로 줄인다.
4. 재개할 때는 받은 알림을 믿지 않는다. 한도에 걸린 동안 도착한 예약·메시지는 처리되지 않았을 수 있다. GitHub PR·Actions와 각 세션 상태를 직접 확인한 뒤 이어 간다.
5. 상위 세션은 알려진 재설정 시각 뒤에 깨어나는 예약을 둘 수 있다. 사용자가 먼저 재개해도 된다.
6. 세션 상태에 사용량 경고가 보이면 확인 주기를 늘리고, 같은 검사를 반복하지 않으며, 새 하위 세션을 줄인다.

Cloudflare D1 무료 한도는 이와 다르다. 매일 00:00 UTC(09:00 KST)에 초기화되는 날짜 단위다. 첫 사용 시각부터 세지 않는다. 적재처럼 한도를 크게 쓰는 작업은 UTC 날짜 하나에 하나만 둔다. 같은 날짜 안이면 시각은 상관없다(사용자와 확인, 2026-10-11T22:50Z).

## Codex 클라우드 환경

기록: 2026-10-10T12:57:03Z / 2026-10-10 21:57:03 KST. 사용자가 전달한 Codex 출력과 화면을 기준으로 했다.

- 환경 `yukemuri`에 세 저장소를 넣었다. 작업의 기본 폴더는 `/workspace`이고 저장소는 `/workspace/<저장소 이름>`에 있다.
- 설치 스크립트는 `cd /workspace/yukemuri && bash scripts/cloud-setup.sh`다. Node 24.19.0·Python 3.12.14·pnpm 11.25.0에서 `cloud-check.py --full`이 통과했다.
- 기본 폴더가 저장소 밖이라 `yukemuri/AGENTS.md`가 자동으로 읽히지 않을 수 있다(미확인). 작업 요청에 이 저장소의 `AGENTS.md`와 인수인계를 읽으라고 적는다.
- 설치 단계에서 `CODEX_HOME`(`/run/codex-environment/codex-home`)에 쓴 파일은 새 작업에 남지 않았다. 환경의 시작 스킬(`start_skill`)도 새 작업에 자동으로 적용되지 않았다. 개인 하네스는 작업마다 첫 메시지로 직접 적용한다.

검토 요청은 세 가지다. 3번은 Codex를 쓸 수 없을 때와 Codex 요청 세 번을 다 쓴 뒤에 쓴다. 검토 기준은 `AGENTS.md`의 ‘Code Review Rules’다. Codex GitHub 리뷰가 공식 문서에서 권장하는 절 제목이다.

1. PR 리뷰: 검토가 필요한 PR에 작성 담당이 `@codex review` 코멘트를 남긴다. 기록 갱신 PR에는 남기지 않는다. CI가 실행되는 PR은 CI 통과 뒤에 남긴다. 문서만 바꿔 CI가 생략되는 PR은 PR을 연 직후 남긴다. 리뷰는 PR 리뷰 코멘트로 남고 작성 세션이 PR 구독으로 받는다. 지적이 없으면 Codex가 👍 반응만 남긴다.
   재검토는 지적을 모두 반영하고 같은 규칙이 적힌 다른 문서까지 맞춘 뒤 한 번만 요청한다. Codex 리뷰는 사용자의 ChatGPT 구독 사용량을 쓰므로 한 PR에서 세 번까지만 요청한다. 세 번째 리뷰에도 지적이 남으면 Codex에는 더 요청하지 않는다(사용자 결정, 2026-10-10). 남은 지적이 P3뿐이면 인수인계의 다음 작업에 적고 병합 조건을 따른다. 지적을 고쳐 마지막 검토 뒤 기록 파일 밖이 바뀌었으면 3번의 ‘이어 가는 Claude 검토’를 사용자에게 묻지 않고 받는다. 그 두 번까지 쓰고도 P0~P2 지적이 남으면 병합하지 않는다. 남은 지적과 판단을 사용자에게 보고한다. 묻지 않고 받는 검토는 여기까지다. 여섯 번째 검토는 사용자의 허락을 받은 뒤에만 요청한다(사용자 결정, 2026-10-11T02:32Z / 2026-10-11 11:32 KST). 답을 기다리는 동안 다른 작업은 이어 간다(사용자 결정, 2026-10-11T15:56Z / 2026-10-12 00:56 KST).
   2026-10-10 [PR #4](https://github.com/jihune/yukemuri/pull/4)에서 확인했다. 요청 뒤 약 3분 만에 P2 지적 3건이 리뷰로 달렸다. 이 저장소의 Code review는 이미 켜져 있었다. 코멘트 없이 연 [PR #3](https://github.com/jihune/yukemuri/pull/3)에는 리뷰가 달리지 않았으므로 요청 코멘트를 남긴다. 리뷰 스레드 답글에 `@codex`를 쓰면 리뷰가 아니라 클라우드 작업 요청으로 처리되어 ‘환경을 만들라’는 안내가 달렸다. 같은 날 [PR #15](https://github.com/jihune/yukemuri/pull/15)에서는 PR 코멘트의 코드 표시 안에 쓴 호출 문구도 리뷰 요청으로 처리되어 한도 안내가 한 번 더 달렸다. Claude 검토 세션이 리뷰 줄 코멘트에 인용한 문구에도 한도 안내가 달렸다. 검토 요청 코멘트 밖의 PR 코멘트·리뷰·답글·PR 설명에는 코드 표시나 인용 안이라도 `@codex`를 쓰지 않는다. 지칭할 때는 ‘Codex 호출 문구’라고 쓴다.
2. 깊은 검토(브라우저 검사 등): 사용자가 Codex 작업을 열어 하네스를 적용한 뒤 검토를 요청한다. 결과를 PR 코멘트로 남기라고 요청에 적는다.
3. Claude 대체 검토(사용자 결정, 2026-10-10T16:28Z / 2026-10-11 01:28 KST): Codex가 사용량 한도 안내를 남기면 그 회차는 Codex에 다시 요청하지 않고 Claude 검토 세션이 대신한다. 요청 뒤 15분 안에 Codex의 요약 코멘트·👀 반응·리뷰·한도 안내가 하나도 없을 때도 같다. 다음 회차에는 같은 PR이라도 Codex에 먼저 한 번 요청하고, 다시 한도 안내가 오면 그 회차도 Claude 검토 세션으로 한다(사용자 결정, 2026-10-18T05:19Z. 하네스 관리 세션에서 사용자가 고른 답 ‘회차마다 한 번 불러 봄’. 그전에는 한도 안내를 받은 PR에서 Codex에 다시 요청하지 않았다). 작성 담당은 그 사실을 PR 코멘트와 인수인계에 적는다. 상위 세션이나 사용자가 그 PR을 구현하지 않은 새 Claude Code 세션을 검토 전용으로 연다. 검토 세션은 다음을 지킨다.
   - `AGENTS.md`의 ‘Code Review Rules’와 이 저장소의 지침을 읽는다. PR head를 받아 필요한 검사를 직접 실행한다.
   - 직접 재현해 확인한 지적만 남긴다. 심각도·파일과 줄·근거·재현 방법을 쓴다.
   - 결과는 PR 리뷰 하나(COMMENT)로 남긴다. 작성 담당과 같은 GitHub 계정으로 게시되므로 첫 줄에 ‘Claude 검토 세션’, 세션 주소, 검토한 커밋을 쓴다. 지적이 없으면 그 사실을 쓴다.

## 개발 DB와 화면 검사

`pnpm dev`는 클라우드 컨테이너에서 실행한다. 사용자 PC 이관이 아니다.
portable 모드는 개발용 인증을 모의한다. 운영 인증 검사를 대신하지 않는다.
Worker 검사는 임시 Miniflare DB를 만들고 정리한다.
개발 화면은 체크인된 자료를 사용하며 운영 D1에 직접 연결하지 않는다.
개인 자료와 운영 DB 백업을 에이전트 레포에 추가하지 않는다.

새 클론의 로컬 D1(`.wrangler/state`, Git 제외)에는 테이블이 없다. 그대로 `pnpm dev`를 열면 `no such table: catalog_meta`로 실패한다. `cloud-check.py --full`의 빌드 뒤, 개발 서버를 멈춘 상태에서 마이그레이션을 한 번 적용한다(2026-10-10T11:48:41Z / 20:48:41 KST 기록). 다시 만들려면 `.wrangler/state`를 지운다.

```bash
rc=0; for f in drizzle/*.sql; do node node_modules/wrangler/bin/wrangler.js d1 execute DB --local --persist-to .wrangler/state --config dist/server/wrangler.json --file "$f" || { rc=$?; echo "실패: $f" >&2; break; }; done; [ "$rc" -eq 0 ]
```

## 지속적인 코드·기록·백업 관리

작업마다 관련 지침·결정·검사·다음 작업을 `docs/work-handoff-latest.md`에 기록하고 코드와 같은 PR에 반영한다. 검토 결과는 검토 담당이 PR에 남기고 작성 담당이 인수인계에 반영한다. 대화 원본은 비공개 아카이브에 보존하고 계정 전체 내보내기를 Git에 넣지 않는다. 긴 대화의 서비스 간 자동 이식은 완료됐다고 주장하지 않는다.

운영 D1은 기존 Sites에 있다. `docs/db-backups.md`를 읽는다. Python 실행기가 일일 백업과 복원 검사를 담당하므로 구독이나 코딩 서비스가 바뀌어도 사용자에게 매번 ZIP 보관을 요구하지 않는다. 스키마 변경 시 실행기의 복원 스키마도 함께 갱신한다.

대용량 공개 seed·이미지·검사 fixture·원래 Git bundle은 `source-assets/`에 해시와 gzip/base64 조각으로 보존한다. `bash scripts/cloud-setup.sh`가 원래 경로와 바이트를 복원한다. 이것은 전송 중단 후 재개를 위한 소스 저장 형식이며 개인 대화·DB 백업이 아니다. 복원된 자료를 수정하면 `python3 scripts/materialize-source-assets.py --pack` 후 `source-assets/` 변경도 같은 PR에 포함한다. 원래 Git 이력만 필요하면 의존성 설치 없이 `python3 scripts/materialize-source-assets.py`를 실행한다.
