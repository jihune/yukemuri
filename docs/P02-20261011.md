## A. 작업 선점

브랜치: `claude/p02-d1-reads`. 시작 기준: main `274f687`.

### 원인

임시 D1에서 선점 질의의 문장별 `rows_read`를 확인했다.

- priority 차선의 정렬식 `missingLinkedDetail`은 후보 작업마다 `hotel_source_groups` 전체(검증 연결 약 20행)를 훑는다. Jalan detail 대기 작업이 약 1.25만 개면 후보 × 연결 수만큼 읽는다(약 29.6만 행).
- 두 차선 모두 적격 작업 전체를 읽어 정렬한 뒤 하나를 고른다. 순서를 주는 색인이 없어서다. refresh(kind 없음)와 list 선점은 `idx_crawl_jobs_provider_lease`를 골라 해당 공급자의 작업 전체를 읽었다.
- 실험: 같은 질의에 `INDEXED BY`로 정렬 색인을 주면 첫 적격 행에서 멈춘다(5,000행 표에서 1행). D1(Miniflare)은 식 색인 `COALESCE(unixepoch(fetched_at),0)`을 받는다.

### 수정

1. 마이그레이션 `0013_robust_reaper.sql`: crawl_jobs 식 색인 2개.
   - `idx_crawl_jobs_claim_priority`: `(provider, kind, status, priority, COALESCE(unixepoch(fetched_at),0), attempts, url)`
   - `idx_crawl_jobs_claim_national`: `(provider, kind, status, COALESCE(unixepoch(fetched_at),0), next_at, attempts, url)`
   - drizzle-kit 0.31.10이 식 색인 SQL을 쉼표에서 잘라 잘못 만들어 SQL 파일만 손으로 고쳤다. 스냅숏(`meta/0013_snapshot.json`)은 생성된 그대로다.
2. `claimCrawlJob()`의 선택 부분. 선택과 임대가 한 UPDATE 문이라는 구조와 임대·준비 시각·활성 임대 조건은 그대로다.
   - kind·status마다 `INDEXED BY`로 한 가지씩 만든다. 각 가지는 차선의 정렬 키(누락 연결 항 제외) 순서로 첫 적격 작업 하나를 고른다.
   - priority 차선이고 detail이 후보에 들면 ‘연결 숙소 상세 누락’ 가지를 하나 더 둔다. 원래 조건식을 그대로 적용한다. Jalan은 연결 묶음이 가리키는 URL을 기본 키로 찾는다. Trip은 상세 id가 연결 묶음의 id인 URL과 상세 표지가 두 번 든 URL만 원래 조건으로 확인한다. 원래 조건이 참이면 반드시 이 둘 중 하나다.
   - 가지들을 `UNION ALL`로 묶고 원래 정렬 키(priority 차선: priority, 누락 여부, 수집 시각, 시도 수, URL / national 차선: 재시도 우선, 수집 시각, next_at, 시도 수, URL)로 하나를 고른다.
   - 같은 결과인 이유: 후보를 kind·status로 나눈 각 묶음의 최솟값 중 최솟값이 전체 최솟값이다. 누락 연결 항은 같은 priority 안에서만 순서를 바꾼다. 최소 priority에 누락 작업이 있으면 누락 가지의 결과가 이기고, 없으면 일반 가지의 결과가 이긴다.

## B. 목록·이름 검색·지도의 검색 스냅숏

브랜치: `claude/p02-search-snapshot`. PR A 브랜치(`4b89297`)에서 시작했다. 코드 커밋 `600adfa`.

### 색인만으로 줄지 않는 이유

- 목록 첫 쪽(`stable=1`)은 조건에 맞는 모든 id를 정렬해 결과 세션에 저장하고, 전체 건수·시설별 수·미확인 제외 수를 함께 돌려준다. 정렬 색인이 있어도 조건에 맞는 행을 모두 읽는다. D1(Miniflare)은 색인 범위 읽기도 행으로 센다. 그래서 필터 없는 목록은 색인으로도 1.2만 행 아래로 내려가지 않는다.
- 이름 부분일치(`instr`)는 색인을 쓸 수 없다. FTS5 trigram은 3글자 미만 검색어를 찾지 못하고, D1 export는 가상 테이블이 있는 DB를 지원하지 않는다는 문서 기록이 있어 쓰지 않았다.
- 지도 범위는 좌표가 payload JSON 안에만 있어 모든 행을 읽는다.

### 설계

1. 마이그레이션 `0014_harsh_thing.sql`: 보조 테이블 `hotel_search_chunks(chunk, version, core, text)` 64행, 뷰 `hotel_search_rows`, trigger 9개.
   - 숙소 하나의 검색 열을 id로 정한 chunk 행의 JSON 객체에 둔다. core는 지역·도도부현·이름·종류·Trip/Jalan 점수와 리뷰 수·천연·시설 비트·확인 비트·위도·경도·생애주기 상태다. text는 검색문·이름·위치·별칭(name_key, 이름)이다.
   - REAL 점수는 `printf('%!.17g')`로(CPU 보강 뒤에는 15자리 표기가 같은 값으로 되읽히면 그 표기, 아니면 17자리), 좌표는 payload의 JSON 원문으로 옮긴다. JavaScript가 SQL이 비교하던 것과 같은 double을 읽게 하기 위해서다(무작위 2만 개 값에서 왕복 차이 0).
   - trigger: hotels·hotel_names·hotel_lifecycle의 INSERT·UPDATE·DELETE(생애주기 UPDATE는 hotel_id·state 열만). 해당 숙소의 기록을 뷰에서 다시 읽어 `json_set`(삭제는 `json_remove`)으로 그 chunk 행을 고치고 version을 올린다. chunk 행이 없으면 아무것도 쓰지 않는다.
2. `lib/hotel-search-snapshot.ts`: 요청마다 version 64행을 읽고 바뀐 chunk만 다시 읽는다. 행이 64개가 아니면(새 D1, 적재 직후, 일부 삭제) 한 문장으로 다시 만든다. 동기화와 행 조립은 isolate 안에서 차례로 실행해 text가 섞이지 않게 했다.
3. `lib/hotel-repository.ts`: 목록 범위(폐업 제외·지역·즐겨찾기·검색어)·시설/평점/리뷰 조건·시설별 수·미확인 제외 수·정렬·쪽·지도 요약·지점·격자를 메모리에서 계산한다. SQL의 의미를 그대로 옮겼다. NULL은 어떤 조건도 만족하지 않고 DESC에서 맨 뒤다. 텍스트 정렬은 SQLite BINARY(코드 포인트) 순서다. 격자 평균은 SQLite AVG(정수 합 뒤 Kahan–Babuska–Neumaier 합)를 따른다. 이름 부분일치는 검색문 포함, 그리고 이름 키가 검색어를 포함하는 숙소와 키를 공유하는 숙소(같은 숙소이거나 같은 도도부현)다. 오타 허용 색인도 스냅숏에서 만든다(2분 갱신은 그대로). hotels는 결과 쪽의 payload만 읽는다.
4. 마이그레이션을 문장 단위로 적용하는 검사·측정 스크립트 12개가 `;`로 나누던 것을 drizzle의 `--> statement-breakpoint`로만 나누게 했다. trigger 본문의 `;` 때문이다.

### 스냅숏 크기

운영 규모 복사본(2026-10-08 행 수로 늘린 임시 D1, 12,271곳)의 chunk 64행 합, UTF-8 바이트. 운영 규모 복사본은 체크인된 1,655곳을 복사해 늘린 것이라 압축률이 실제보다 좋게 나온다(gzip 9 전체 core 208KB, brotli 11 text 149KB는 복사본 반복 때문). 그래서 복사하지 않은 1,655곳만 압축하고 12,271/1,655배(7.41배)로 늘린 값을 추정치로 쓴다.

| 조각 | 내용 | 원본 | gzip 9 추정 | brotli 11 추정 |
|---|---|---:|---:|---:|
| core | 지역·도도부현·이름·종류·Trip/Jalan 점수와 리뷰 수·천연·시설 비트·확인 비트·위도·경도·생애주기 상태 | 약 1.73–1.79MB | 약 357KB | 약 277KB |
| text | 검색문·이름(ko/ja/en)·위치·별칭(name_key, 이름) | 약 6.75–6.92MB | 약 1.20MB | 약 757KB |

- 참고: hotels payload 전체는 약 23.5MB(운영 규모 복사본)다. 목록 카드에 필요한 필드만 담은 조각은 따로 재야 한다(아래 ‘열린 점’).
- 이 컨테이너 Node 24에서 `JSON.parse`: core 약 12–18ms, text 약 27–30ms(64행 합). 브라우저(특히 모바일) 시간은 미측정이다.

- `lib/hotel-alternatives.ts`(조건 없는 결과 때 대안 순위): 위 모듈만 쓴다. 지금은 서버에서만 부른다.

#38에서 메모리 계산으로 옮긴 부분(`lib/hotel-repository.ts`, `lib/hotel-search-snapshot.ts` @ `143941f`). 순수 함수라 그대로 옮길 수 있다:

- 범위·조건: `eligible`(시설·평점·리뷰·료칸, NULL은 어떤 조건도 만족하지 않음), `unknownOnly`(사실이 없어서만 빠진 수), `inScope`(폐업·휴관 제외, 지역·도도부현, 즐겨찾기, 검색어 결과).
- 집계: 시설 비트별 수(설정된 비트만 셈), 료칸 수, 유사 이름 수.
- 이름 부분일치 `substringMatches`: 검색문 포함 + 이름 키가 검색어를 포함하는 숙소와 키를 공유하는 숙소(같은 숙소이거나 같은 도도부현).
- 정렬 `sortedRows`: 추천(천연 → Trip 9.0+·리뷰 50+ → 평점 → 리뷰 → id)·평점·리뷰·이름. NULL은 DESC 맨 뒤, 텍스트는 SQLite BINARY(코드 포인트) 순서(`textOrder`·`compareText`, 서로게이트 쌍 처리). 검색어가 있으면 추천순 안에서 이름 관련도로 안정 정렬.
- 지도 `computeMapArea`: 범위 안 지점(500개까지, id 순), 넘으면 16×16 격자와 SQLite AVG 방식(`sqliteAverage`, 정수 합 뒤 Kahan–Babuska–Neumaier)의 평균. 좌표는 위도·경도가 둘 다 JSON 숫자일 때만.
- 원래 SQL과 같은 결과라는 근거: #38의 응답 비교(211개 요청 × 쓰기 전후, 422개 main과 같음, 변형 4종 실패). 브라우저로 옮긴 뒤에도 같은 비교(서버 main 응답 대 브라우저 계산)를 쓰면 된다.

서버 전용이라 바꿔야 하는 의존성:

- D1 읽기(`favoritesDb`): 스냅숏 동기화(`hotel_search_chunks`), 결과 쪽 payload(`hotelPayloads`·`hotelsInOrder`), 출처 묶음(`attachSourceGroups`)·생애주기(`attachLifecycle`), 수집 현황(`readCachedCoverage`), 결과 세션(`createResultSession`·`readResultSession`). 정적 스냅숏에서는 앞의 셋이 스냅숏 조각이나 Worker의 id 묶음 조회로, 결과 세션은 브라우저 상태로 바뀐다.
- 즐겨찾기만 보기: 서버가 방문자 키로 즐겨찾기 id를 읽는다(`visitorFavoriteIds`). 브라우저 계산이면 즐겨찾기 API가 준 id 목록으로 거른다.

- 오타 허용 색인은 지금 서버가 만들어 `/api/hotels/search-index`로 보낸다(새 isolate 약 500ms). 정적 스냅숏이면 Actions가 색인 입력을 만들거나 브라우저가 text 조각에서 만든다.

### 열린 점(P03에서 정할 것)

- 목록 카드 자료: 지금 목록 응답은 쪽마다 숙소 payload 전체(사진·설명 포함)와 출처 묶음·생애주기를 붙인다. 카드용 필드만 담은 조각을 정적으로 둘지, 쪽의 id 40개를 Worker가 D1에서 읽을지(PR A 기준 결과 세션 2쪽이 522행, 비교 3곳이 75행) 정해야 한다.
- 스냅숏 갱신 시점과 일관성: 수집 실행 끝에 한 번 만들면 그 사이의 생애주기 patch·출처 묶음 변경·즐겨찾기는 다음 실행까지 늦게 반영된다. 결과 세션(목록 순서 유지) 대신 스냅숏 버전을 쓰면 된다.
- 텍스트 조각(약 1.2MB gzip)을 첫 방문에 받을지, 검색어를 입력할 때 받을지.
- 정적 자산 무료·무제한, Worker 호출로 세지 않음은 상위 세션이 확인한 Cloudflare 문서 기준이다. 이 세션에서는 문서를 열지 못했다.
