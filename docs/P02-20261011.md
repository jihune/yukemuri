## A. 작업 선점

브랜치: `claude/p02-d1-reads`. 시작 기준: main `274f687`.

### 원인

임시 D1에서 선점 질의의 문장별 `rows_read`를 확인했다.

- priority 차선의 정렬식 `missingLinkedDetail`은 후보 작업마다 `hotel_source_groups` 전체(검증 연결 약 20행)를 훑는다. Jalan detail 대기 작업이 약 1.25만 개면 후보 × 연결 수만큼 읽는다(약 29.6만 행).
- 두 차선 모두 적격 작업 전체를 읽어 정렬한 뒤 하나를 고른다. 순서를 주는 색인이 없어서다. refresh(kind 없음)와 list 선점은 `idx_crawl_jobs_provider_lease`를 골라 해당 공급자의 작업 전체를 읽었다.
- 실험: 같은 질의에 `INDEXED BY`로 정렬 색인을 주면 첫 적격 행에서 멈춘다(5,000행 표에서 1행). D1(Miniflare)은 식 색인 `COALESCE(unixepoch(fetched_at),0)`을 받는다.

### 수정

1. 마이그레이션 `0013_robust_reaper.sql`: crawl_jobs 식 색인 2개.
   - `idx_crawl_jobs_claim_priority`: `(provider, kind, status, priority, COALESCE(unixepoch(fetched_at),0), attempts, url)`
   - `idx_crawl_jobs_claim_national`: `(provider, kind, status, COALESCE(unixepoch(fetched_at),0), next_at, attempts, url)`
   - drizzle-kit 0.31.10이 식 색인 SQL을 쉼표에서 잘라 잘못 만들어 SQL 파일만 손으로 고쳤다. 스냅숏(`meta/0013_snapshot.json`)은 생성된 그대로다.
2. `claimCrawlJob()`의 선택 부분. 선택과 임대가 한 UPDATE 문이라는 구조와 임대·준비 시각·활성 임대 조건은 그대로다.
   - kind·status마다 `INDEXED BY`로 한 가지씩 만든다. 각 가지는 차선의 정렬 키(누락 연결 항 제외) 순서로 첫 적격 작업 하나를 고른다.
   - priority 차선이고 detail이 후보에 들면 ‘연결 숙소 상세 누락’ 가지를 하나 더 둔다. 원래 조건식을 그대로 적용한다. Jalan은 연결 묶음이 가리키는 URL을 기본 키로 찾는다. Trip은 상세 id가 연결 묶음의 id인 URL과 상세 표지가 두 번 든 URL만 원래 조건으로 확인한다. 원래 조건이 참이면 반드시 이 둘 중 하나다.
   - 가지들을 `UNION ALL`로 묶고 원래 정렬 키(priority 차선: priority, 누락 여부, 수집 시각, 시도 수, URL / national 차선: 재시도 우선, 수집 시각, next_at, 시도 수, URL)로 하나를 고른다.
   - 같은 결과인 이유: 후보를 kind·status로 나눈 각 묶음의 최솟값 중 최솟값이 전체 최솟값이다. 누락 연결 항은 같은 priority 안에서만 순서를 바꾼다. 최소 priority에 누락 작업이 있으면 누락 가지의 결과가 이기고, 없으면 일반 가지의 결과가 이긴다.

### 호환성

- 테이블·열은 바꾸지 않았다. `catalog-export`의 표·열과 `schema: '0012'` 표시는 그대로다. 실행기 백업(`run-backup.py`)은 manifest의 `schema`와 자기 사본(0000–0012)의 열을 비교하므로 영향이 없다. 실행기 PR은 필요 없다.

- H01: 3단계(2026-10-11T12:13–12:17Z, run 38138420167)에서 만든 D1 `yukemuri`에는 0000–0012만 적용됐다. 0013은 다음 `wrangler d1 migrations apply`(자동 배포가 켜진 첫 배포 또는 D1 setup 재실행) 때 적용된다. 4단계 적재 전에 적용되면 crawl_jobs 적재 때 색인 두 개도 쓰고, 적재 뒤면 색인을 만들 때 쓴다. 어느 쪽이든 crawl_jobs 15,417행 기준 약 3.1만 행을 한 번 더 쓰므로 적재 일정(하루 쓰기 10만 행)에 넣어야 한다.

## 부가 조사: 개발 서버 첫 요청의 `Network connection lost`

U04 세션 보고(main `274f687`에서 새 로컬 D1의 개발 서버 첫 요청이 4회 중 2회 `importSnapshot`에서 실패)를 조사했다.

- 재현 방법: 새 로컬 D1(`rm -rf .wrangler/state` 뒤 `cloud-development.md`의 마이그레이션 적용), `node scripts/run-framework.mjs dev`, 준비 확인은 Worker를 거치지 않는 `/@vite/client`로 하고, `/api/hotels`를 한 번 요청한다(제한 400초). 실패하면 같은 서버에 한 번 더 요청한다. 스크립트는 세션 임시 폴더에만 있었다.
- 결과(12:05Z–13:00Z, 같은 컨테이너): 지금 코드(seed를 동적 import)는 19회 중 8회 실패했다. P01 PR B 이전처럼 seed를 정적 import로 바꾼 임시 변형은 8회 모두 성공했다. 두 상태를 번갈아 잰 8회(D·S·S·D·D·S·S·D)에서는 둘 다 실패가 없었다. 연속 실행(같은 상태로 서버를 다시 연 경우)에서 실패가 몰렸다. 차이는 통계적으로 확정되지 않았다(실패 8/19 대 0/8).
- 실패 위치는 매번 `importSnapshot()`의 `import('./hotel-catalog')`(Promise.all 0번)였다. 개발 서버에서 동적 import는 `@cloudflare/vite-plugin` 1.37.1의 `runInRunnerObject()`가 모듈 실행용 Durable Object에 RPC로 넘긴다. 실패는 요청 뒤 5–8초에 `Network connection lost`로 끝났다. 실패 뒤에는 같은 서버의 다음 요청도 약 0.1초 만에 같은 오류로 실패했다. 서버를 다시 열 때까지 회복되지 않았다. 성공하면 첫 요청은 seed 적재까지 약 92–106초 걸렸다.
- 판단: P01 PR B의 seed 지연 로드가 개발 서버의 동적 import 경로를 타게 만든 것과 관련이 있다. 실패 자체는 Vite 개발 서버의 모듈 실행기 안에서 난다. 빌드된 Worker(Miniflare)에서는 같은 동적 import가 이 작업의 측정·비교·검사 수십 회에서 한 번도 실패하지 않았다. 운영 Worker에는 해당하지 않는다고 본다. 왜 Durable Object 연결이 끊기는지(메모리·시간 한도 등)는 확인하지 못했다.
- 고치지 않았다. 이 작업 범위(요청당 D1 읽기)의 코드가 아니고, 정적 import로 되돌리면 운영 Worker가 모든 요청에서 4.77MB seed를 평가한다(P01 PR B가 줄인 시작 비용). 대안 후보는 (가) 빌드된 Worker로 로컬 D1을 한 번 채운 뒤 `pnpm dev`를 여는 도우미, (나) seed JSON을 문자열로 불러와 모듈 크기를 줄이는 방법이다. 둘 다 시험하지 않았다. 당장은 실패하면 개발 서버를 다시 열고 `/api/hotels`를 먼저 요청한다(U04 기록과 같음).
