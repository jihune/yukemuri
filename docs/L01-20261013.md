### 1.2 H01 전환 뒤 운영에서 쓰이는 방식

- `update-lifecycle.py`는 주소를 표준입력으로 받는다. 옛 Sites 주소에 고정되어 있지 않다. `source_safety.site_api()`가 Sites 두 주소와 `https://yukemuri.<서브도메인>.workers.dev`를 받는다. workers.dev에는 `X-Yukemuri-Crawl-Key`만 보낸다(`check_site_access.py`가 단언한다).
- 유지관리 키 요청은 H02의 자동화 UA 거절·상세 속도 제한보다 먼저 통과한다(`lib/edge-guard.ts`).
- 그러나 Cloudflare 운영에서 이 도구를 부르는 workflow는 없다. `collect.yml`은 `update-site.py`만 실행한다. 키는 앱 레포 Secret `YUKEMURI_CRAWL_ACCESS_KEY`와 Worker Secret `CRAWL_ACCESS_KEY`에만 있다. 그래서 지금은 키를 가진 사람이 직접 실행해야만 공식 상태를 바꿀 수 있다. 이 개발 세션은 키를 쓰지 않으므로 바꿀 수 없다.
- 상세(`/api/hotels/<id>`)는 Worker가 D1에서 바로 읽으므로 저장 즉시 바뀐다. 목록·검색·지도는 정적 스냅숏이라 다음 스냅숏 생성 때 바뀐다. 스냅숏은 main push 배포와, 1쪽 이상 맡은 gentle 수집 뒤의 배포(`collect.yml` → `deploy.yml`)에서 만든다. 그날 D1 예산이 다 써서 수집이 0쪽이면 스냅숏도 다시 만들지 않는다.
- `onsen-first-plan-20261005.md`의 실행 예시는 Sites 시절 방식(같은 Site의 `get_site`로 `{url,token}`을 얻음)이다. 지금 운영과 맞지 않는다.
- `scripts/check-lifecycle-worker.mjs`(lifecycle API의 Worker 검사)는 `cloud-check.py`에 들어 있지 않은 CI 밖 검사다. 마지막 실행 기록은 2026-10-12 P03 작업의 통과다(`P03-20261012.md` ‘CI 밖 검사’).
- `update-lifecycle.py`는 409·404 같은 HTTP 오류를 받으면 예외로 끝난다. 그 뒤의 근거는 보내지 않는다.

## 2. 반영 경로 설계(상위 세션 답을 기다린다)

운영 쓰기 경로를 새로 여는 일이라 설계를 상위 세션에 먼저 보낸다. 새 Secret과 사용자 조치는 필요 없다.

1. 근거 파일 `data/lifecycle-official.json`: `{"version":1,"patches":[…]}`. 각 항목은 Worker 계약(`lib/lifecycle-contract.ts`)과 같은 필드만 쓴다. 기록 id 하나에 항목 하나다. 첫 내용은 1.4의 다섯 근거를 운영 값 그대로 옮긴 것이다. 그래서 첫 실행은 다섯 건 모두 `replayed`(쓰기 0)로 경로만 확인한다.
2. PR 검사(`cloud-check.py` 기본 목록, 키 없음): `scripts/check-lifecycle-official.mjs`가 `lib/lifecycle-contract.ts`를 그대로 컴파일해 모든 항목을 검사한다. 더해서 id 중복, 출처가 예약 사이트(Jalan·Trip.com 등) 주소인 것, 근거 확인일이 미래인 것을 거절한다. 고장 낸 사본(미래 효력일, 예약 사이트 출처, 중복 id, 모르는 필드)이 실패하는지도 같은 검사에서 본다.
3. 적용 workflow `.github/workflows/lifecycle.yml`(이름 ‘Yukemuri lifecycle’):
   - 시작: 이 파일을 바꾼 main push와 수동 실행만. `pull_request`에서는 돌지 않는다. cron 없음.
   - 잠금: `yukemuri-catalog-updates`(`cancel-in-progress: false`, `queue: max`). 수집·배포와 겹치지 않는다.
   - Secret: 기존 `YUKEMURI_CRAWL_ACCESS_KEY`를 적용 단계 env에만 준다. 대상은 `cloudflare-deploy.json`의 `publicOrigin`이다(`run-collection.py`의 `target_origin`·`load_key`·`child_env`를 그대로 쓴다). 키는 `update-lifecycle.py` 표준입력으로만 간다.
   - `update-lifecycle.py` 보완: 근거 하나가 409(더 새 근거가 있음)·404(모르는 기록)·400을 받아도 나머지를 계속 보내고, 끝에 실패 수만큼 실패로 끝낸다. 결과 줄(`saved`·`replayed`·`stale`·`unknown`)을 남긴다.
   - 하나라도 `saved`면 `uses: ./.github/workflows/deploy.yml`(`after_collection: true`, `secrets: inherit`)로 스냅숏을 다시 만든다. 수집 workflow와 같은 방식이다. 모두 `replayed`면 배포하지 않는다.
4. 다시 실행해도 결과가 같다: 같은 근거는 `replayed`이고 쓰기가 없다. 오래된 확인일 덮어쓰기 거절(409)은 Worker에 그대로 둔다.
5. 파일에서 항목을 지워도 운영 상태는 되돌아가지 않는다. 상태를 바꾸려면 더 늦은 확인일의 새 근거(예: 재개장 확인 뒤 `operating`)를 넣는다.
6. D1 사용량(추정, 구현 PR에서 임시 D1로 잰다):
   - 새 근거 한 건: `hotel_lifecycle` 갱신 1행과 색인, `hotel_lifecycle_events` 1행과 색인. 4~5행 쓰기다.
   - `replayed` 한 건: 쓰기 0. 읽기는 기록 조회 2번과 다시 읽기 한 번(상세 조합)이다.
   - 스냅숏 재생성: 읽기 약 11.5만 행(`cloudflare-deploy.md` 수집 workflow 절의 1회 측정 114,598행). `saved`가 있을 때만 돈다.
   - 이 파일을 바꾼 main push는 `deploy.yml` push 배포도 부른다(경로 제외 목록에 없음). 그래서 근거를 더한 병합 한 번에 스냅숏을 최대 두 번 만든다. 하루 읽기 한도 500만의 약 5%다.
7. 검사: 가짜 Worker로 `update-lifecycle.py`의 결과별 처리와 키가 출력에 남지 않는지 본다(`check_site_access.py` 방식). `check-lifecycle-worker.mjs`를 돌려 PUT 경로가 그대로인지 본다. `check-collect-workflow.mjs`·`check-deploy-config.mjs`의 workflow 공통 단언(읽기 전용 토큰, PR에 Secret 없음, `queue: max`, cron 없음)이 새 파일에도 걸린다.
