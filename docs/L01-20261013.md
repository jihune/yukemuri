### 1.2 H01 전환 뒤 운영에서 쓰이는 방식

- `update-lifecycle.py`는 주소를 표준입력으로 받는다. 옛 Sites 주소에 고정되어 있지 않다. `source_safety.site_api()`가 Sites 두 주소와 `https://yukemuri.<서브도메인>.workers.dev`를 받는다. workers.dev에는 `X-Yukemuri-Crawl-Key`만 보낸다(`check_site_access.py`가 단언한다).
- 유지관리 키 요청은 H02의 자동화 UA 거절·상세 속도 제한보다 먼저 통과한다(`lib/edge-guard.ts`).
- 그러나 Cloudflare 운영에서 이 도구를 부르는 workflow는 없다. `collect.yml`은 `update-site.py`만 실행한다. 키는 앱 레포 Secret `YUKEMURI_CRAWL_ACCESS_KEY`와 Worker Secret `CRAWL_ACCESS_KEY`에만 있다. 그래서 지금은 키를 가진 사람이 직접 실행해야만 공식 상태를 바꿀 수 있다. 이 개발 세션은 키를 쓰지 않으므로 바꿀 수 없다.
- 상세(`/api/hotels/<id>`)는 Worker가 D1에서 바로 읽으므로 저장 즉시 바뀐다. 목록·검색·지도는 정적 스냅숏이라 다음 스냅숏 생성 때 바뀐다. 스냅숏은 main push 배포와, 1쪽 이상 맡은 gentle 수집 뒤의 배포(`collect.yml` → `deploy.yml`)에서 만든다. 그날 D1 예산이 다 써서 수집이 0쪽이면 스냅숏도 다시 만들지 않는다.
- `onsen-first-plan-20261005.md`의 실행 예시는 Sites 시절 방식(같은 Site의 `get_site`로 `{url,token}`을 얻음)이다. 지금 운영과 맞지 않는다.
- `scripts/check-lifecycle-worker.mjs`(lifecycle API의 Worker 검사)는 `cloud-check.py`에 들어 있지 않은 CI 밖 검사다. 마지막 실행 기록은 2026-10-12 P03 작업의 통과다(`P03-20261012.md` ‘CI 밖 검사’).
- `update-lifecycle.py`는 409·404 같은 HTTP 오류를 받으면 예외로 끝난다. 그 뒤의 근거는 보내지 않는다.

동작:

1. 같은 근거를 다시 보내면 `replayed`이고 쓰기가 없다. 저장된 것보다 오래된 확인일은 Worker가 409로 거절한다(그대로 둠). 파일을 바꾸지 않고 다시 실행해도 결과가 같다.
2. 파일에서 항목을 지워도 운영 상태는 되돌아가지 않는다. 상태를 바꾸려면 더 늦은 확인일의 새 근거(예: 재개장을 확인한 뒤 `operating`)를 넣는다.
3. 스냅숏은 근거를 저장한 뒤 한 번 만든다. 모두 `replayed`면 만들지 않는다.
   - 이 파일만 바꾼 병합: `deploy.yml` push 배포가 돌지 않는다(`paths-ignore`). `lifecycle.yml`이 배포를 한 번 부른다.
   - 다른 파일도 바뀐 병합: push 배포도 돈다. `lifecycle.yml`은 실행 내내 수집 잠금을 쥐므로, 같은 커밋의 push 배포가 아직 끝나지 않았다면 그 배포는 반드시 이 실행 뒤에 돌고 그 스냅숏에 새 근거가 들어간다. 그래서 `lifecycle.yml`은 배포를 부르지 않는다. push 배포가 이미 끝났다면(근거 저장 전에 만든 스냅숏) `lifecycle.yml`이 한 번 더 만든다.
   - API가 답하지 않으면 스냅숏을 직접 만든다. 스냅숏이 하나 더 생기는 쪽(읽기 약 11.5만 행)이 새 상태가 다음 수집까지 빠지는 쪽보다 낫다고 봤다.
   - 수동 실행과 재실행(`run_attempt`가 1이 아님)에서는 저장한 근거가 없어도(모두 `replayed`) 스냅숏을 만든다. 앞선 실행이 근거를 저장한 뒤 스냅숏 배포가 실패했을 수 있기 때문이다. 기다리는 push 배포가 실패한 경우도 수동 실행으로 다시 만든다.
4. 거절된 근거가 있어도 저장된 근거는 스냅숏에 들어간다. 그 뒤 판정 job이 실행을 실패로 끝낸다. 적용 단계는 거절 때문에 실패하지 않는다. 실패한 단계의 출력이 다음 job에 넘어가는지 기대지 않기 위해서다.

첫 실행에서 기대하는 결과(파일 6건): 운영 값을 그대로 옮긴 4건은 Worker 계약으로 파싱한 문자열이 운영 근거와 바이트까지 같다. 그래서 `replayed`(쓰기 0)다. 하코네 유모토 호텔(확인일 갱신)과 하코네 하이랜드 호텔(새 근거) 2건은 `saved`다. 그래서 스냅숏을 한 번 만든다. 바이트 비교는 15:39Z에 컴파일한 계약과 1.4의 공개 상세 응답으로 했다. 실제 결과는 병합 뒤 실행에서 확인한다.
