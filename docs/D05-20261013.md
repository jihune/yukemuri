## 4. 설계

### 4.1 필드

숙소 payload(`lib/hotel-types.ts`의 `Hotel`)에 두 가지를 더한다.

| 이름 | 형식 | 값의 뜻 |
|---|---|---|
| `features.viewBath` | 기존 `FeatureFact` | `true`: 출처에 전망 욕탕이 있다(‘있음’). 값이 없거나 `null`: ‘확인 필요’. Jalan에는 ‘없음’ 표기가 없어 `false`를 만들지 않는다. `scope`는 `property`. `note`에 원문(예: `展望風呂（条件有り）`)을 남긴다 |
| `rooms` | `{total:number; byType?:{western:number;japanese:number;japaneseWestern:number;other:number}; sourceId:string; verifiedAt:string; note:string}` | 있으면 출처가 밝힌 총 객실 수다. 없으면 ‘확인 필요’다. `byType`은 Jalan 표의 洋室·和室·和洋室·その他다. Trip.com은 `total`만 있다 |

- 이름표: `viewBath`는 ‘전망 욕탕’이다. Jalan의 `展望風呂`는 온천수인지 말하지 않으므로 ‘전망 온천’이라고 쓰지 않는다. 천연온천 여부는 기존 `natural`로 따로 본다.
- `viewBath`는 시설 키 목록(`EXTRA_FEATURE_LABELS`)의 맨 끝, `jalanHighClass` 뒤에 둔다. 그러면 기존 비트 0–12의 순서가 그대로이고 `viewBath`는 비트 13이다. 기존 행의 비트 13은 0이라 ‘확인 필요’로 읽힌다.
- 객실 사진 필드(`roomPhotos`)는 3.3의 결정 뒤 후속 PR에서 정한다.

### 4.2 파서(`scripts/crawler/collect.py`)

- Jalan 상세: `shisetsu-roomsetsubi_body` 안 첫 표의 머리 칸과 값 칸을 짝지어 읽는다. `総部屋数`가 1 이상의 정수일 때만 `rooms`를 만든다. 칸 이름이 다르거나 값이 숫자가 아니면 만들지 않는다(‘확인 필요’).
- Jalan 상세: `その他の風呂施設`와 `風呂利用条件` 행에 `展望風呂`·`展望大浴場`·`展望露天`이 있으면 `viewBath=true`다. 숙소 밖 시설 안내(기존 `external_bath`)일 때는 다른 욕탕 사실처럼 비운다.
- Trip.com 상세: 이 숙소의 `hotelDescriptionInfo.lables`에서 `객실 수: N`만 읽어 `rooms.total`로 둔다. 추천 숙소 묶음이 아닌 이 숙소의 묶음인지 `masterHotelId`나 묶음 위치로 확인한다.
- 목록 쪽은 바꾸지 않는다.

### 4.3 계약·합성·API

- `lib/crawl-contract.ts`: `rooms`를 선택 필드로 받는다. `total`은 1–5,000 정수, `sourceId`는 그 숙소 id, `verifiedAt`은 날짜다. `viewBath`는 `FEATURE_LABELS`에 넣으면 지금 코드가 선택 필드로 받는다.
- `lib/source-policy.ts`의 `composePreferredHotel`: 연결된 출처가 있으면 `rooms`를 시설 우선순위(Jalan → Trip.com)로 고르고, 같은 순위면 더 새 관측을 쓴다. `viewBath`는 지금 시설 합성이 그대로 처리한다.
- 상세 API(`/api/hotels/<id>`)와 비교 API는 합성한 `Hotel`을 그대로 보내므로 `rooms`·`features.viewBath`가 따라 나간다.
- 스냅숏: `viewBath`는 `core.features`·`core.known` 비트 13과 `cards[].features.viewBath`로 나간다. `SNAPSHOT_FORMAT`은 바꾸지 않는다(키 추가). `rooms`는 스냅숏에 넣지 않는다. 카드·필터에 객실 수가 필요해지면 U05와 정한다.

### 4.4 D1 쓰기·읽기

### 4.5 이미 상세를 수집한 숙소

- Jalan(1,429곳): 기존 ‘baths’ 단계를 쓴다. 이 단계는 Jalan 파서가 새 항목을 읽게 됐을 때 기존 상세를 다시 받으려고 만든 것이다. 수집기가 붙이는 `bathDataVersion`을 `v1`에서 `v2`로 올리고, 선점 조건을 ‘`v2`가 아닌 숙소’로 바꾼다. gentle 실행은 한 바퀴(8단계)에 baths 1쪽을 쓴다. 120쪽 실행이면 약 15쪽, 하루 8번이면 약 120쪽이다. 그러면 약 12일이면 다 돈다(추정). 그동안 같은 수만큼 다른 단계의 쪽이 줄어든다. 실행당 상한·사이트 간격·대기 규칙은 바꾸지 않는다.
- 대안은 판 번호를 올리지 않고 정기 재확인(온천 지역 7일 – 전국 45일, `data/collection-priorities.json`)만 기다리는 것이다. 쪽 배분은 그대로지만 끝나는 시점을 예측하기 어렵다. 권장은 판 번호 올리기다.
- Trip.com(756곳): 객실 수는 정기 재확인과 새 상세 수집으로 채운다. 판 번호를 따로 두지 않는다.

### 4.6 화면에 생기는 영향

- `components/hotel-card.tsx`는 모든 시설 키를 돌며 ‘있음’ 표지를 그린다. 그래서 `viewBath`를 시설 키에 넣으면 컴포넌트를 고치지 않아도 지금 카드에 ‘전망 욕탕’ 표지가 나온다.
