대상은 체크인된 자료(`lib/hotels.real.json` 20개, `lib/hotels.crawled.json` 1,634개, `lib/hotels.verified.json` 1개, 합계 1,655개)다. 운영 D1의 약 12,000개 기록은 이 환경에서 읽지 않았다.

## 지역 표기 대조

방법: `node scripts/audit-region-labels.mjs docs/evidence/d01-region-audit-20261010.json`. 앱과 같은 정규화(`lib/hotel-catalog.ts`)를 적용한 뒤 두 가지를 본다.

1. 저장된 `prefecture`와 주소에서 읽은 도도부현이 같은가.
2. 화면 지역명(`formatHotelLocation`)의 첫 지명이 주소에 있는가. 온천 지역이면 그 온천 패턴이, 시정촌이면 그 일본어·영어 이름이 주소에 있어야 한다.

결과(수정 후):

| 항목 | 개수 |
|---|---|
| 도도부현 일치 | 1,646 |
| 도도부현 불일치 | 0 |
| 주소가 비어 도도부현 판정 불가 | 9 (Trip, 도쿄 8·지바 1) |
| 온천 지역명이 주소와 일치 | 196 |
| 온천 지역명을 이름·표기에서 얻음 | 39 |
| 시정촌명이 주소와 일치 | 1,411 |
| 시정촌명이 주소에 없음 | 9 (위 빈 주소 9개) |

대조 검사: `lib/hotels.verified.json`의 도도부현을 임시로 오사카로 바꾸면 `prefecture-mismatch: 1`이 나왔다. 원래 파일로 되돌렸다.

이름·표기에서 온천 지역명을 얻은 39개는 하나씩 보았다. 주소의 시정촌이 그 온천의 시정촌과 같았다(예: `月岡温泉` 이름과 `新潟県新発田市月岡`). 지역 오류로 보지 않았다.

### 코드가 원인인 오류

수정 전에는 큐레이션한 홋카이도 숙소 8개의 지역명에서 온천 지역이 빠졌다. 원인은 `lib/japan-place-labels.ts`의 온천 패턴 준비 코드 두 곳이다.

1. 로마자 부분을 찾는 검사 `/[a-z]/i`가 정규식 이스케이프 `\s`의 `s`도 로마자로 보았다. 그래서 `노보리베츠\s*온천` 같은 한국어 부분에도 단어 경계 `\b`가 붙었다. JavaScript의 `\b`는 한글을 단어 문자로 보지 않으므로 이 한국어 부분은 어떤 표기와도 맞지 않았다.
2. 공급자의 로마자 주소는 접미사를 붙여 쓴다(`Yunokawacho`, `Jozankeionsen`, `Noboribetsuonsencho`). 패턴 끝의 `\b` 때문에 `yunokawa`가 `Yunokawacho`와 맞지 않았다.

수정: 이스케이프를 지운 뒤 로마자를 찾는다. 로마자 부분 끝은 `\b` 대신 `onsen`·`cho`·`chō`·`machi` 또는 단어 경계를 허용한다. 수정 전후 1,655개의 지역명을 비교해 아래 8개만 바뀌었다. 모두 주소의 지명과 맞는다.

### 코드 밖의 자료 문제(고치지 않음)

- Trip 기록 9개는 주소가 비어 있다. 지역은 목록 표기(`도쿄`, `지바`)에서만 왔다. 시정촌을 확인할 수 없다. 예: `trip-705045` Toyoko Inn Narita Airport Honkan은 `지바`로 표시되지만 숙소명은 나리타 공항이다.
- 주소가 있는 Trip 기록 15개는 모두 도시명과 번지가 두 번 붙어 있다(예: `Yokohama4-chōme-29-1 Tsurumichūō4-chōme-29-1 Tsurumichūō, Tsurumi Ward, ...`). 도도부현·시정촌 판정에는 영향이 없었다. 수집기의 Trip 주소 조합 문제로 보이며 원인은 확인하지 않았다. 수집기 수정은 Sites 게시 전까지 예약 실행에 반영되지 않으므로 별도 작업으로 남긴다.

## 동일 숙소 연결

기준: 공급자 ID·원어명·주소·판매 범위가 모두 맞을 때만 연결을 제안한다. 체크인된 자료에서 기준을 충족한 새 연결은 0건이다. 반영안은 없다.

| 후보 | 근거 | 판정 |
|---|---|---|
| `trip-994895` Shinagawa Prince Hotel ↔ `jalan-340595` 品川プリンスホテル | 영어·일본어 이름이 같은 호텔을 가리킴 | 미확인. Trip 주소가 비어 있다. 같은 주소에 `jalan-347464` 品川プリンスホテル Ｎタワー가 별도 상품으로 있다. Trip 상품이 본관만인지 N타워를 포함하는지 확인해야 한다 |
| Jalan 내부 같은 주소 11곳(9쌍·3개 묶음 2곳) | 주소만 같음 | 연결하지 않음. Jalan이 별도 ID로 파는 별관·다른 브랜드·다른 상품으로 보인다. 쌍마다 공식 자료를 확인하지는 않았다. 예: `jalan-306800` 그랜드 프린스 신타카나와와 `jalan-313492` 그랜드 프린스 타카나와, `jalan-327980` 積善館 佳松亭와 `jalan-372584` 積善館 本館, `jalan-329246` 등 나가시마 리조트 호텔 3곳 |
| 큐레이션 20개의 Trip·Jalan 상세 ID | 기존 검증 숙소에 저장된 정확한 공급자 ID | 체크인된 수집 자료에는 해당 ID 기록이 없다. 운영에서는 `importVerifiedSourceGroups`가 이미 이 링크로 연결을 만든다 |
| `jalan-303587` ↔ `trip-5515405` 하코네 묘진다이 | `data/hotel-mapping-reviews.json`의 기존 검토 | 두 ID 모두 체크인된 자료에 없다. 리브랜드·회원 객실 범위 검토가 그대로 남는다 |

체크인된 Trip 기록 24개의 이름은 영어이고 Jalan 기록은 일본어다. 이름 문자열로는 자동 대조가 되지 않는다. 영어 이름을 일본어로 바꿔 Jalan을 찾은 결과 Shinagawa 외에는 같은 도도부현의 같은 숙소가 없었다. 체인 이름만 같은 다른 지점(아파·도요코인·다이와 로이넷 등)은 연결하지 않았다.

## 운영 반영안

- 지역명 수정: 코드 게시만 필요하다. D1 변경은 없다.
- 동일 숙소 연결: 이번에 제안할 연결은 없다. 연결할 때는 보호된 `POST /api/hotel-source-groups`에 `lib/source-group-contract.ts` 형식(`hotelId`, 공급자 ID, `matchedName`, 출처 URL, 20자 이상의 `identityEvidence`, `sameInventory: true`, `checkedAt`)으로 보낸다. 근거를 확인하지 못한 후보는 보내지 않는다.
- 운영 자료 전체(약 12,000개)의 지역 대조는 하지 않았다. 체크포인트를 새 로컬 DB에 복원한 세션에서 `scripts/audit-catalog.py`로 공급자 간 후보를 뽑고, 이 문서의 기준으로 판정한다. 지역명 대조는 `audit-region-labels.mjs`가 체크인 파일만 읽으므로 입력 경로를 받도록 확장해야 한다.
