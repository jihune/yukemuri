## 할 것

1. 앱 저장소 PR(먼저 병합): 매시간이면 그날 D1 예산을 다 쓴 뒤의 실행은 정상적으로 `pages=0`이 된다. 지금 매일 점검(`scripts/daily-check.mjs`)은 그날 0쪽 실행이 하나라도 있으면 실패로 끝나므로, 이대로 두면 날마다 거짓 실패 메일이 간다. 0쪽을 실패로 볼 조건을 정해 고친다. 예: 그날 `reason=`이 예산 소진(쓰기·읽기 몫 0)으로 0쪽인 실행은 정상으로 보고, 사용량을 읽었는데 한도에 여유가 있는데도 0쪽이거나 그날 gentle 실행이 모두 0쪽이면 실패. 대조 입력(`zero-pages`)도 새 규칙에 맞춘다. 주석의 ‘3시간마다’(`collect.yml` 첫 주석, `scripts/collection-budget.mjs`의 `maxPages`, `scripts/check-collect-workflow.mjs`의 ‘three lost dispatches’ 줄)를 고친다. 12시간 공백 감시(`collect-watch.yml`, 실행기의 `check`)는 바꾸지 않는다.
2. 실행기 저장소 PR(앱 PR 병합 뒤): `.github/workflows/yukemuri-catalog.yml`의 cron과 dispatch 조건의 `github.event.schedule` 값을 매시간으로 바꾼다. 분은 정각 근처를 피한다(GitHub 문서: 정각이 붐빈다). 다른 예약(`yukemuri-backup.yml`, `yukemuri-daily-check.yml` 01:41Z)과 같은 분을 피한다. `scripts/check-dispatch-app-collection.py`의 cron 단언, `docs/runner.md`·`README.md`의 ‘3시간’ 문구, `project-files.json` 항목을 함께 고친다.
3. 비용을 숫자로 적는다.
   - 실행기(비공개 저장소) Actions 분: 지금 하루 약 5회에서 최대 24회. 실행마다 올림 1분이면 한 달 약 740분이 는다. 계정 무료 2,000분/월 안인지, 지금 실행기 사용 분(백업·점검 포함)을 실행 목록으로 다시 세어 적는다(GitHub 플랜은 미확인).
   - D1: 실행마다 그날 사용량을 다시 읽고 자기 스냅숏 몫(`snapshotReads`)을 남기므로 85% 상한은 지켜진다. 실행이 늘면 스냅숏 생성 읽기(약 12만 행)가 실행 수만큼 늘어 읽기 몫이 먼저 닿을 수 있다. 하루 실행 10회 안팎일 때 쓰기·읽기 어느 쪽이 쪽수를 묶는지 어림을 적는다.
   - Cloudflare 배포: 쪽이 0이 아닌 실행마다 스냅숏 배포가 한 번 돈다. Workers 무료 요금제에 하루 배포 횟수나 정적 파일 업로드 제한이 있는지 공식 문서로 확인하고 날짜·방법을 적는다(하네스 `source-freshness`).
4. 바꾼 뒤 이틀(UTC 날짜 둘) 동안 실제 실행 수, 0쪽 실행 수, 하루 처리 쪽수, D1 쓰기·읽기 비율을 재서 이 문서에 적는다. 근거 스크립트는 `docs/evidence/h01-schedule-gap-20261018/slot_gaps.py`를 cron에 맞게 써도 된다.

- 바깥 근거: GitHub 문서의 schedule 설명(`github/docs` 저장소 `data/reusables/actions/schedule-delay.md`, raw 파일을 10-21T02:13Z `curl`로 받음)에 ‘If the load is sufficiently high enough, some queued jobs may be dropped.’라고 적혀 있다. 커뮤니티 글 https://github.com/orgs/community/discussions/209507 은 이 세션에서 직접 받을 수 없었다(`curl` 403, 세션에 붙은 저장소 밖 GitHub 경로). 요약 도구 WebFetch가 10-21T02:1xZ에 돌려준 인용으로는 제목이 ‘Scheduled workflow runs delayed by several hours despite valid cron’, 첫 글이 2026-10-04(15분마다 도는 예약)이고, 10-19 댓글에 ‘However, observing only 13 runs across 192 nominal slots suggests a substantial scheduling degradation.’가 있다. 두 출처 모두 예약 실행이 늦거나 빠질 수 있다는 근거이고, 하루 5번이라는 값은 이 저장소의 측정이다.
