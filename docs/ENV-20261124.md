## 맡은 일

사용자가 2026-11-19에 고른 ‘11-25 뒤 옮기기 (권장)’의 준비 PR이다. `CLOUDFLARE_API_TOKEN`과 `YUKEMURI_CRAWL_ACCESS_KEY`를 저장소 secret이 아니라 환경 `production`의 secret으로 옮기고, 그 환경은 배포 브랜치를 `main`으로 제한한다. 이 PR은 workflow와 검사만 바꾼다. 환경 만들기, 브랜치 제한, 환경 secret 넣기, 저장소 secret 지우기는 사용자가 GitHub Settings에서 한다(이 세션은 Settings를 바꾸지 않는다). 병합은 11-25 `readsPerPage` PR #329 병합 뒤이고, 사용자가 환경 설정을 끝낸 날 상위 세션이 한다.

까닭: #322의 job `if: github.ref == 'refs/heads/main'` 지킴은 고른 브랜치 자신의 workflow 파일에 있어서 브랜치가 지우면 사라지고, `collect-chain.yml`과 `usage.yml`에는 없다(`docs/V01G-20261117.md` 「남은 일」). 환경의 배포 브랜치 제한은 저장소 Settings에 있어 브랜치가 고칠 수 없다.

## 사용자 단계와 순서

<!-- steps:begin -->
값은 채팅에 쓰지 않는다. 각 단계를 마치면 상위 세션에 ‘완료’만 알린다. 화면 이름은 2026-11-24에 공식 문서(`docs.github.com`의 Managing environments for deployment)에서 읽은 것이다. 화면이 다르면 그 화면을 상위 세션에 알린다.

먼저 준비물이다. 두 값(Cloudflare API 토큰, 수집 키)은 지금 저장소 secret에 있는 것과 같은 값이어야 한다. GitHub는 저장된 secret을 다시 보여 주지 않으므로 원래 값을 따로 보관하고 있어야 한다. 수집 키는 배포가 Worker의 `CRAWL_ACCESS_KEY`로 올리므로 값이 달라지면 Worker의 키가 바뀐다. 값을 보관하고 있지 않으면 여기서 멈추고 상위 세션에 알린다(새 값 만들기는 기존 Secret 회전이라 이번 범위 밖이다, `AGENTS.md`).

병합 전에 사용자가 하는 일(1~4):

1. 저장소 `jihune/yukemuri` → Settings → 왼쪽 Environments → New environment. 이름에 `production`을 입력하고 Configure environment를 누른다(이름은 대소문자를 구분하지 않지만 철자가 다르면 다른 환경이 만들어진다).
2. 같은 화면의 Deployment branches 드롭다운에서 Selected branches and tags를 고르고 Add deployment branch or tag rule → Ref type Branch → 이름 패턴 `main` → Add rule. 저장 뒤 환경 화면의 규칙 목록에 `main`이 보이는지 본다(이 단계를 빠뜨리거나 Protected branches only를 고르면 아무것도 실패하지 않은 채 제한이 걸리지 않는다. 문서는 Protected branches only에 ‘If no branch protection rules are defined for any branch in the repository, then all branches can deploy.’라고 적는다). Protected branches only는 고르지 않는다. Required reviewers, Wait timer, Custom deployment protection rules는 켜지 않는다(켜면 시간마다 도는 수집과 배포가 승인이나 대기에서 멈춘다).
3. 같은 환경 화면의 Environment secrets 아래 Add secret으로 `CLOUDFLARE_API_TOKEN`과 `YUKEMURI_CRAWL_ACCESS_KEY` 두 개를 넣는다. 값은 이 입력란에만 붙여 넣는다. 저장소 secret은 지우지 않는다. 저장 뒤 환경 화면의 Environment secrets 목록에 두 이름이 보이는지 본다.
4. 상위 세션에 ‘환경 완료’를 알린다. 상위 세션이 이 PR을 병합한다. 병합은 코드를 바꾼 main push라 `deploy.yml`이 곧 운영에 배포한다.

병합 뒤에 사용자가 하는 일(5~7):

5. 병합 직후의 배포(Actions의 Cloudflare deploy)와 그 뒤 첫 수집(Actions의 Yukemuri collection, 매시간 37분 예비 부르기, 수집 끝의 스냅숏 배포 포함)이 모두 초록인지 상위 세션과 함께 본다. 이 시점에는 저장소 secret이 남아 있어도 같은 이름의 환경 secret이 먼저 쓰인다(공식 문서).
6. (필수) 제한이 실제로 걸렸는지 본다. 병합된 main에서 새 브랜치를 하나 만들고(Code 탭 브랜치 드롭다운에 이름을 입력해 Create branch) Actions의 Cloudflare usage(읽기 전용 점검)를 그 브랜치로 Run workflow한다. 환경 제한이 걸렸으면 job이 시작되지 않고 브랜치가 허용되지 않는다는 오류로 끝난다. 이 결과를 상위 세션에 알리고 시험용 브랜치는 지운다. 거절되지 않고 점검이 돌았다면 제한이 걸리지 않은 것이므로 7을 하지 않고 상위 세션에 알린다. 이 단계는 2단계의 제한이 실제로 걸렸는지 보이는 유일한 단계이고, 문서가 직접 보장하지 않는 부분의 확인이다(아래 「미확인」 1).
7. 5가 초록이고 6이 거절로 끝났으면 Settings → Secrets and variables → Actions의 Repository secrets에서 `CLOUDFLARE_API_TOKEN`과 `YUKEMURI_CRAWL_ACCESS_KEY`를 지운다. `CLOUDFLARE_ACCOUNT_ID`는 지우지 않는다(이 PR은 두 값만 옮긴다). 같은 화면에는 환경 secret도 함께 나열되므로(Using secrets 문서: ‘If your repository has environment secrets …, then those secrets are also listed on this page.’) 지울 곳은 Repository secrets 칸이고, Environment secrets 칸의 같은 이름은 지우지 않는다. 그 뒤 첫 수집과 스냅숏 배포가 초록이면 끝이다. 빨강이면 지운 두 저장소 secret을 같은 값으로 다시 넣고 상위 세션에 알린다. 코드는 바꾸지 않아도 된다(아래 「미확인」 2).

순서가 틀렸을 때 멈추는 것:

- 환경을 만들기 전에 병합한다: 병합 직후 배포가 `production`을 보호 규칙도 secret도 없는 환경으로 자동 만든다(공식 문서). 저장소 secret이 남아 있어 배포는 돈다. 대신 main 제한이 걸리지 않은 채 돌며, 사용자가 그 환경에 2~3(브랜치 제한과 환경 secret)을 하면 이어진다.
- 환경 이름 철자가 다르다: 철자가 다른 환경이 자동으로 만들어져 제한도 secret도 없다. 저장소 secret이 남아 있는 동안은 돌지만 보호가 없다. 저장소 secret을 지운 뒤라면 토큰과 키가 빈 값이라 배포·수집·사용량 점검이 인증 실패로 멈춘다.
- 환경 secret을 넣기 전에 저장소 secret을 지운다(7을 3보다 먼저): 같은 실패다. 수집이 멈추고 12시간 감시(`collect-watch.yml`)가 알린다. 사이트는 마지막 배포 그대로 남는다. 두 값을 환경에 넣으면 풀린다.
- 배포 브랜치 이름 패턴이 `main`과 다르다: `main`에서 도는 모든 job이 ‘브랜치가 허용되지 않는다’로 시작하지 못해 배포·수집이 모두 멈춘다. 패턴을 `main`으로 고치면 풀린다.
- Required reviewers나 Wait timer를 켠다: 수집과 배포가 승인이나 대기 시간에서 멈춘다(`deployment: false`여도 적용된다, 공식 문서).
- 6을 하지 않고 7을 한다: 제한이 걸렸는지 모른 채 저장소 secret을 지워, 제한이 없어도 아무것도 실패하지 않고 보호만 없다(2단계 문장).
- 환경 secret 값이 원래와 다르다: 다음 배포가 Worker의 `CRAWL_ACCESS_KEY`를 새 값으로 바꾼다. 같은 키를 쓰는 다른 곳(실행기 저장소의 백업·점검, 이 세션이 확인하지 못함)이 거절당한다.

값이 있는 곳의 목록(값은 적지 않는다): `jihune/yukemuri`의 저장소 secret `CLOUDFLARE_API_TOKEN`·`YUKEMURI_CRAWL_ACCESS_KEY`(7에서 지움)·`CLOUDFLARE_ACCOUNT_ID`(그대로), 같은 저장소의 환경 `production`의 secret(3에서 넣음). 실행기(private) 저장소의 secret은 건드리지 않는다.

## 바꾼 것

비밀값을 읽는 job을 `grep -rnE 'CLOUDFLARE_API_TOKEN|YUKEMURI_CRAWL_ACCESS_KEY' .github/workflows`로 다시 세었다(main `dd7ce511fd5399c3a4651f79fd292bba6d2b03f4`). 파일 일곱, job 일곱이다. 같은 일곱을 `scripts/check-secret-environment.mjs`가 파일을 읽어 따로 찾는다.

| 파일 | job | 읽는 값 | 시작 경로 |
|---|---|---|---|
| `collect.yml` | `collect` | 토큰, 키 | `workflow_dispatch`(실행기·`collect-spare.yml`이 `--ref main`) |
| `deploy.yml` | `deploy` | 토큰, 키 | main push, `workflow_dispatch`, `workflow_call`(`collect.yml`·`lifecycle.yml`의 `snapshot`이 세 secret을 이름으로 넘김) |
| `collect-chain.yml` | `wait` | 토큰 | `workflow_dispatch`(`collect.yml`의 `chain` job이 `--ref main`) |
| `d1-setup.yml` | `d1` | 토큰 | 수동 |
| `lifecycle.yml` | `apply` | 키 | `data/lifecycle-official.json`을 바꾼 main push, 수동 |
| `rollback.yml` | `rollback` | 토큰 | 수동 |
| `usage.yml` | `usage` | 토큰 | `workflow_dispatch`(실행기가 `--ref main`) |

일곱 job에 같은 블록을 더했다(`environment:` 아래 `name: production`, `deployment: false`). 환경 이름은 이 세션이 `production`으로 정했다. 철자가 쉽고, 배포·수집·점검이 모두 같은 운영 자원(Cloudflare 계정과 Worker)을 쓰므로 환경 하나로 충분하다. 블록은 각 job에서 기존 검사가 줄 붙임을 요구하는 자리(`outputs:` 바로 뒤의 `steps:`, `permissions:` 바로 뒤의 `steps:` 등)를 피해 놓았다.

환경을 더하지 않은 job: `collect.yml`의 `snapshot`(`uses:` job은 `environment`를 쓸 수 없다)과 `chain`, `lifecycle.yml`의 `snapshot`(같은 까닭)과 `verdict`. `collect-spare.yml`, `collect-watch.yml`, `web-checks.yml`은 두 값을 읽지 않는다. 두 값이 아닌 `CLOUDFLARE_ACCOUNT_ID`는 이 PR이 옮기지 않는다(사용자가 정한 것은 두 값). 계정 ID만으로는 Cloudflare API를 쓸 수 없다는 것이 이 세션의 판단이다.

`deploy.yml`을 부르는 두 곳(`collect.yml`과 `lifecycle.yml`의 `snapshot` job)은 `secrets: inherit` 대신 `deploy.yml`이 읽는 세 secret(`CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN`, `YUKEMURI_CRAWL_ACCESS_KEY`)을 `${{ secrets.이름 }}`으로 이름으로 넘기고, `deploy.yml`의 `on.workflow_call.secrets`는 그 셋을 `required: true`로 선언한다(상위 세션이 2026-11-24에 공식 문서를 다시 보고 정한 것). 까닭: Reuse workflows는 환경에만 있는 secret을 넘기는 방법으로 이름으로 넘기기를 분명히 적는다(‘You can pass a secret by name even if it only exists in the environment.’). `secrets: inherit`가 사용자 7단계로 저장소 secret을 지운 뒤에도 그 값을 넘기는지는 문서에 없고, 넘기지 않으면 오류 없이 빈 값으로 돈다(‘If the caller workflow doesn't pass an environment secret, the secret resolves to an empty string in the reusable workflow. The workflow run doesn't show an error. To make the workflow run fail instead, set required: true for the secret in on.workflow_call.secrets.’). `required: true`는 부르는 쪽이 넘겼는지만 보고 값이 있는지는 보지 않는다. 부르는 `snapshot` job은 환경을 달 수 없고(‘The job that calls the reusable workflow can't use the environment keyword.’) 환경 값은 불린 `deploy` job이 받는다(‘The job that sets environment receives the environment secret's value.’). Workflow syntax의 `jobs.<job_id>.secrets.inherit` 설명(‘This includes all secrets the calling workflow has access to, namely organization, repository, and environment secrets.’)은 부르는 쪽 job의 접근 범위를 말하므로 이 경로를 직접 뒷받침하지 않는다. 이 변경 때문에 `scripts/check-collect-workflow.mjs`와 `scripts/check-lifecycle-official.mjs`가 글자 그대로 단언하던 `snapshot` job의 `secrets: inherit` 줄을 세 줄로 바꿨고, 후자의 ‘크롤 키는 한 번만 이름이 나온다’ 단언은 apply 단계의 한 번과 `snapshot` 호출의 세 이름으로 바꿨다. `docs/cloudflare-deploy.md` 151행의 `secrets: inherit` 설명도 고쳤다.

`scripts/run-actionlint.py`: 고정한 actionlint 1.7.7이 `environment.deployment` 키를 모른다(‘unexpected key "deployment" for "environment" section’). `concurrency.queue`와 같은 방식으로 그 메시지 하나만 무시 목록에 더했다. 키 자체는 `check-secret-environment.mjs`가 글자 그대로 단언한다.

새 검사 `scripts/check-secret-environment.mjs`(`cloud-check.py` 기본 목록, `check-rollback-workflow.mjs` 다음)가 하는 일:

- `.github/workflows`의 `.yml`·`.yaml` 파일 모두에서 job마다 두 값을 읽는지 보고, 읽는 job은 위 블록을 정확히 하나 가져야 하고 읽지 않는 job은 환경이 없어야 한다.
- 읽는 job의 목록이 일곱(`EXPECTED`)과 다르면 실패한다. 새 job이 두 값을 읽으면 블록을 더하고 이 목록에 올려야 한다.

## 미확인

1. `deployment: false`를 단 job에 배포 브랜치 제한이 실제로 걸리는지. 문서의 보호 규칙 표는 필수 검토자·대기 시간·사용자 지정 규칙 앱만 행으로 적고 배포 브랜치 제한 행이 없다. 같은 쪽의 쓰임새 목록(“Access control—restrict which branches can use certain secrets via environment branch policies, without deployment tracking.”)이 근거의 전부이고, 실행해 보지 않았다. 사용자 6단계(필수)가 읽기 전용 `usage.yml`로 확인한다. 제한이 걸리지 않는 것으로 나오면 일곱 workflow의 `deployment: false` 줄과 검사의 `BLOCK` 한 줄을 지우면 되고, 그때는 job마다 deployment 기록이 남는다.
2. 이름으로 넘긴 secret이 불린 `deploy.yml`의 `deploy` job에 환경 값으로 닿는지. 문서가 이 방식을 환경에만 있는 secret의 방법으로 적고(위 (나)와 「바꾼 것」의 인용) 환경 secret이 이긴다고 적었지만 실행해 보지 않았다. 저장소 secret이 남아 있는 동안은 환경 secret과 저장소 secret이 같은 이름이라 닿았는지 구분되지 않는다. 사용자 7단계로 저장소 secret을 지운 뒤 첫 수집 스냅숏 배포(`collect.yml`의 `snapshot`)와 `lifecycle.yml`의 `snapshot`이 처음 시험한다. 실패하면 저장소 secret을 다시 넣어 풀고 상위 세션에 알린다. `required: true`는 넘겼는지만 보므로 빈 값은 인증 실패로 드러난다.
3. 환경에 secret이 없고 저장소 secret만 있을 때 환경을 단 job이 저장소 secret을 읽는지. 문서에 그 문장이 직접 없고, 같은 이름이 두 단계에 있으면 환경 쪽이 이긴다는 문장에서 읽었다. 이것은 「사용자 단계」 순서의 ‘병합 직후 저장소 secret이 남아 있어 배포가 돈다’가 기대는 부분이다. 3단계에서 두 값을 모두 환경에 넣으므로 이 PR의 순서(1~4 뒤 병합)에서는 이 경우가 걸리지 않는다.
4. 값. 사용자가 두 값을 가지고 있는지, 실행기(private) 저장소가 같은 수집 키를 쓰는지(`docs/H02-20261013.md`의 `YukemuriBackup/1.0` 요청이 같은 키를 쓴다고 읽히지만 그 저장소는 이 세션이 보지 않는다).
