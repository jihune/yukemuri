## 판단 근거

1. 하네스 `START.md` 4단계의 ‘다음 메시지를 기다린다’는 요청이 작업을 지정해 따르지 않았다. `STATE.md`·요청 원장은 `AGENTS.md`가 별도 기록 폴더를 금지해 이 문서와 인수인계에 기록했다. Windows 경로·PowerShell·winget 지침은 Linux 클라우드라 적용하지 않았다.
2. 배포 값은 환경 변수가 아니라 커밋된 `cloudflare-deploy.json`에 두었다. 요청이 ‘저장소의 배포 설정 파일에서 읽는다’고 했고, 3단계 ID 기록과 4단계 뒤 자동 배포 켜기가 모두 PR 하나로 남는다.
3. Workers Caching(`cache.enabled`)은 쓰지 않았다. 문서(`workers/cache/`, 원본 `0d35c2c`)상 켜면 정적 파일 요청도 Worker 요청 수로 세고, `Cache-Control` 없는 응답도 기본 TTL로 저장한다. 무료 하루 10만 요청과 즐겨찾기 응답 보호에 불리하다.
4. 속도 제한 키는 IP다. Cloudflare 문서는 IP 키를 권장하지 않는다(여러 이용자가 IP를 공유). 이 사이트는 로그인이 없고 이용자는 사용자 한 명이라 IP가 남는 유일한 키다. 한도는 사람 한 명의 검색·지도 이동보다 넉넉하게 60초 120회로 두었다. 5단계에서 조정할 수 있다.
5. 배포 workflow가 `cloud-check.py --full`을 다시 실행한다. main push의 `checks`와 별개로 돌아서 그 결과를 기다리지 않기 때문이다. 앱 레포가 public이라 Actions 시간은 무료다.
6. P01 B(#31)와 겹치는 `lib/hotel-repository.ts`·`app/api/crawl/route.ts`는 건드리지 않았다. 보호 기능은 Worker 진입점에 두었다.
