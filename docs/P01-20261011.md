# P01 응답 속도와 D1 읽기량 줄이기

기록: 2026-10-11T07:45:00Z / 2026-10-11 16:45:00 KST(A). B: 2026-10-11T09:05:00Z / 18:05:00 KST.
작업 환경: Claude Code 웹 클라우드(Ubuntu 24.04). 상위 세션이 맡긴 작업이다.
출발점은 `hosting-review-20261011.md`의 1.9절(코드로 추정한 D1 사용량)과 3.5절(위험)이다.
작업은 PR 둘로 나눈다. A는 측정 검사와 수집 저장 경로·집계 캐시다. B는 목록·이름 검색의 전체 스캔, 첫 요청의 색인·백필, seed 번들이다.
호스팅·운영 D1·Secret·수집 예약·공유 범위는 바꾸지 않았다. DB 스키마(마이그레이션)도 바꾸지 않았다. Sites에는 게시하지 않았다.

## 측정 방법

`node scripts/measure-d1-reads.mjs [--grow] [--check] [--out 파일]`.

- 빌드된 Worker(`dist/server`)를 임시 폴더에 복사하고 임시 Miniflare D1에 마이그레이션 13개를 적용한다. 운영 DB에 연결하지 않는다.
- 측정용 진입 모듈이 앱의 `env.DB`를 감싼다. 요청마다 D1 결과의 `meta.rows_read`·`meta.rows_written`과 문장 수를 더한다. 1,000행 이상 읽은 문장은 SQL 앞부분과 함께 남긴다. `dist/` 자체와 앱 코드는 바꾸지 않는다.
- `--grow`는 체크인된 기록을 새 ID로 복사해 2026-10-08 계정 내보내기의 행 수(hotels 12,271·hotel_names 13,849·crawl_jobs 15,417)까지 늘린다. 복사본은 이름이 원본과 같아서 이름 검색의 일치 수가 운영보다 많을 수 있다. 작업 대기열 복사본도 원본의 상태 분포를 그대로 가진다.
- 시간은 이 컨테이너의 벽시계 시간이다. 로컬 SQLite를 포함하고 한 번만 잰다. 운영 D1 지연이나 Worker CPU 시간이 아니다.
- **미확인**: Miniflare가 `rows_read`를 운영 D1과 같은 방식으로 세는지 확인하지 못했다. 두 쪽 모두 SQLite 통계를 쓴다고 알려져 있으나 이 작업에서 운영 값과 대조하지 않았다.
- 새 isolate 요청(`listCold`·`nameCold`·`crawlPutCold`)은 같은 DB로 Miniflare를 새로 띄워 잰다. 모듈 캐시(검색 색인·집계 캐시·카탈로그 준비)가 비어 있는 상태다.
- 수집 요청은 실제 실행 순서를 따른다. 이전 실행이 끝의 GET으로 집계를 남긴 뒤, 작업 선점 POST와 상세 1곳 PUT을 잰다.
- `--check`는 P01 상한을 단언한다. 상한은 hotels 행 수에 비례하게 둔다. 수집 PUT은 hotels의 2% 이하, PUT 뒤 이름 검색은 ‘색인 있는 이름 검색’ + hotels의 2% 이하다. `cloud-check.py --full`이 체크인 규모로 실행한다.

## A. 수집 저장 경로와 집계 캐시

브랜치: `claude/p01-d1-reads`(PR #28). 시작 기준: main `1ff8f48`(PR #24 병합). 코드 커밋: `da919d5`, Codex 지적 수정 `fa99371`.

### 원인

- `PUT /api/crawl`은 응답의 `coverage`를 만들려고 매번 `queryCoverage()`를 불렀다. 이 함수는 hotels 전체(COUNT·COUNT DISTINCT)와 crawl_jobs 전체(공급자별 합계)를 훑는다.
- `writeHotels()`가 부르는 `indexNames()`는 끝에서 `invalidateSearch()`를 불렀다. 그래서 수집 쓰기마다 그 isolate의 이름 색인·결과 캐시·집계 캐시가 모두 비었다. 다음 이름 검색은 색인을 다시 만들었다(약 7.8만 행 추가).
- 수집기(`scripts/crawler/update-site.py`)는 PUT 응답에서 `coverage.records`만 읽어 진행 줄에 쓴다. 실행 끝 GET의 `coverage`는 통째로 출력한다.

### 수정

1. 기록 수 카운터: `catalog_meta`의 `hotel-records` 행이다. 스키마는 그대로다. hotels 행은 `writeHotels()`만 넣고 지우는 코드가 없다. `writeHotels()`는 100행 묶음마다 한 트랜잭션(`db.batch`)에서 카운터를 먼저 올리고 upsert한다. 올리는 값은 묶음 안의 서로 다른 id 중 아직 hotels에 없는 수다. 기본 키 조회라 묶음 크기만큼만 읽는다.
2. `readCachedCoverage()`: 최대 5분 된 집계 위에 카운터의 정확한 `records`(`crawledRecords = records − 20`)를 얹는다. PUT·재전송 PUT·검색 화면이 쓴다. 카운터가 아직 없으면 수집 요청은 전체를 세고 카운터를 만든다. 검색 화면은 집계 값을 그대로 쓴다.
3. `readCoverage()`: 수집 끝 GET이 쓴다. 지금처럼 전체를 센다. 같은 D1 batch(트랜잭션) 안에서 카운터를 `COUNT(*)`로 다시 쓴다. 첫 실행·백업 복원 뒤처럼 카운터가 틀린 경우 한 실행 안에 바로잡는다. 겹친 PUT의 쓰기는 이 트랜잭션 앞(이미 셈)이나 뒤(바로잡힌 값에 더함)에 놓인다. 그래서 GET 한 번에 hotels를 한 번 더 센다(약 1.2만 행).
4. 수집 쓰기는 결과 캐시만 비운다. 이름·주소 부분일치는 hotels·hotel_names를 직접 읽으므로 새 숙소는 바로 검색된다. 오타 허용 색인(검색어 예측 포함)과 집계 캐시는 타이머(색인 2분, 집계 5분)로 갱신된다. 이 쓰기를 받지 않은 다른 isolate는 원래 이 타이머로만 갱신됐다. 관리 편집(이름·생애주기·출처 연결)의 `invalidateSearch()`와 일회성 이름 재색인 끝의 비우기는 그대로다.
5. 검색 화면 수집 현황의 집계 캐시는 30초에서 5분으로 늘었다. 수집 쓰기가 더는 비우지 않는다. 기록 수는 카운터로 정확하다. 발견·완료·대기·실패 수는 최대 5분 늦을 수 있다.

수집기 파일(`scripts/crawler/*`)은 바꾸지 않았다. 수집기 release는 다시 만들어지지 않는다. 응답 필드 이름과 형태는 그대로다.

## B. 검색 전체 스캔·첫 요청·seed

브랜치: `claude/p01-search-scans`. PR A 브랜치(`ef6c1e8`)에서 시작했고 A의 Codex 수정 뒤 A 브랜치(`ea324a9`)를 merge했다. 코드 커밋: `3c613c4`, merge 해결 `ef8df77`, Codex 지적 수정 `5e860ba`.

### 실험으로 확인한 원인

임시 D1에서 문장 하나씩 `rows_read`를 쟀다(운영 규모 복사본).

- `id NOT IN (SELECT hotel_id FROM hotel_lifecycle WHERE state IN (...))`는 hotels 행마다 임시 표를 한 번 찾아 그 수만큼 더 센다. hotels 전체를 읽는 문장 하나가 12,271행이 아니라 24,542행이 된다. 같은 뜻의 `NOT EXISTS (SELECT 1 FROM hotel_lifecycle l WHERE l.hotel_id=hotels.id AND ...)`는 12,273행이다. `hotel_lifecycle.hotel_id`는 NOT NULL 기본 키라 두 식의 결과가 같다.
- 정렬(`ORDER BY` 계산식)은 정렬기를 거치며 한 번 더 센다(12,271 → 24,542). 정렬 열 색인 없이 줄이기 어려워 두었다.
- 이름 부분일치(`instr(search_text)` + `hotel_names` 이름 키 일치)는 한 번에 약 26,400행이다. 목록 문장과 집계 문장이 각각 이 식을 품어 두 번 계산했다.
- 오타 허용 색인은 hotels 1,500행마다 별칭 하위 질의를 숙소마다 실행해 약 7,000행을 읽었다.
- 새 isolate는 `backfillBathFacts()`의 `bath_features IS NULL` 확인으로 hotels 전체(12,271행)를 읽었다. 색인이 없는 열이다.
- 새 isolate에서 집계 캐시가 비어 있으면 첫 검색과 첫 PUT이 수집 집계(약 2.8만 행)를 다시 셌다.
- 4.77MB seed(`lib/hotels.crawled.json`)는 `hotel-repository` 청크 안에 들어 있어 모든 API 라우트가 정적으로 불러 평가했다.

### 수정

1. 폐업·임시휴업 제외를 `NOT EXISTS`로 바꿨다(목록·집계·지도·색인).
2. 이름 부분일치를 요청마다 한 번만 실행해 id 목록을 얻는다. 목록·집계 문장은 그 목록과 오타 허용 일치 id를 합친 `id IN (json_each)`로 일치 행만 읽는다. 일치 집합은 이전 식과 같다.
3. 색인 생성 때 별칭을 한 번에 기본 키 순서(`hotel_id, name_key`)로 읽는다. 이전 하위 질의가 돌려주던 순서와 같다. 페이지마다 별칭 범위를 읽는 방식도 시험했으나 문장 수가 27개로 늘어 택하지 않았다(지금 19개).
4. bath 백필은 빈 값이 없음을 한 번 확인하면 `catalog_meta`의 `bath-facts-backfill-v1`에 완료를 적는다. `writeHotels()`는 항상 값을 채워 넣으므로 이후 행은 확인할 필요가 없다.
5. 수집 끝 GET이 집계를 `catalog_meta`의 `coverage-snapshot`에 `{seq, coverage}`로 저장한다. `seq`는 집계를 읽는 트랜잭션 안에서 올리는 `coverage-sequence` 값이다. 저장된 `seq`보다 클 때만 덮어써서 늦게 끝난 GET이 오래된 집계를 저장하지 않는다(Codex 지적, `5e860ba`). 다른 isolate는 메모리 캐시가 없으면 이 값(행 2개)을 읽는다. 기록 수는 A의 카운터로 정확하다. 발견·완료·대기·실패 수는 마지막 수집 실행 끝의 값이다. 저장값이 없으면 지금처럼 센다.
6. seed 분리: `lib/catalog-core.ts`에 관리 숙소 20곳·검증 숙소·집계 버전만 둔다. 4.77MB seed(`hotel-catalog.ts`)와 수집 대기열 seed(`data/crawl-jobs.json`)는 DB를 처음 채우거나 검증 연결을 처음 가져올 때만 동적 import한다. 수집 PUT의 관리 숙소 id는 `curatedCatalogHotels`에서 만든다. seed 청크는 Worker 번들에 남는다. 새 D1을 처음 채우는 데 필요하기 때문이다. 번들에서 빼려면 seed 적재를 배포 단계로 옮겨야 한다(H01 계획과 함께 정할 일).

스키마(마이그레이션)는 바꾸지 않았다. 새 `catalog_meta` 키는 `bath-facts-backfill-v1`, `coverage-snapshot`, `coverage-sequence` 세 개다(A의 `hotel-records` 포함 네 개). 수집기 파일은 바꾸지 않았다.

### 남은 비용과 미확인

- 목록 첫 쪽은 여전히 hotels를 세 번 정도 읽는다(정렬된 id 전체 24,542 + 집계 12,271). 결과 세션(`stable=1`)이 모든 id를 순서대로 저장하는 설계라서다. 줄이려면 정렬 열 색인(스키마 변경)이나 공용 응답 캐시(H01 계획의 익명 검색 캐시)가 필요하다.
- 이름 검색의 부분일치는 `instr` 전체 스캔(약 2.6만 행)이 남는다.
- 작업 선점 POST(약 6.4천 행)와 catalog-export 목록은 A와 같이 두었다.
- 4.77MB seed 청크는 번들에 남는다. 평가만 미룬다. 운영 Worker의 CPU 시간은 재지 못했다(로컬 벽시계 시간만 있음).
