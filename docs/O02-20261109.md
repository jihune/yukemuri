# O02 — 매시간 수집 부르기 예비를 public 앱 레포 예약으로

기록: 2026-11-09T12:2xZ / 21:2x KST. 작성 세션은 하위 세션 `session_01Up3F21Xbu4ao2sZvDnhVUG`이고, 상위 세션 `session_01Up3F23nhK2tW2PjhYzZYnC`(열아홉 번째)가 맡겼다. 브랜치 `claude/o02-actions-minutes`, 변경 등급 2(workflow와 검사 스크립트를 바꾼다). 병합은 상위 세션이 한다. `docs/work-handoff-latest.md`와 `docs/roadmap.md`는 이 PR에서 고치지 않는다.

## 배경

- GitHub 계정의 Actions 포함 사용량은 월 2,000분이고 private 저장소만 센다. public 저장소의 표준 러너는 무료다. 이 계정은 GitHub Free이고 매달 1일에 초기화된다(`roadmap.md` 결정 기록 ‘GitHub 플랜과 Actions 사용 분’).
- private 실행기 저장소 `jihune/yukemuri-script-runner`의 `yukemuri-catalog.yml`이 cron `37 * * * *`로 이 앱 저장소의 `collect.yml`(mode gentle)을 매시간 부른다. 이 예비가 고리(C06)가 끊긴 날 수집을 다시 잇는다. 이 workflow의 10월 실행은 183분이었다(10-01–10-12 79분, 10-13–10-31 104분). 11-01–11-03에는 9분(하루 3번쯤)이다. 근거는 상위 세션 기록 브랜치 `claude/yukemuri-parent-19`의 `docs/evidence/o02-20261103/`(`runs-by-wf.txt`, `minutes-1031-1102.csv`)에 있고, 상위 세션의 기록 PR이 main에 넣기 전에는 main에 없다.
- 사용자가 2026-11-03T04:4xZ에 ‘둘 다 넣음 (권장)’으로 정했다(`work-handoff-latest.md` 「상위 세션 인계」 2). 이 PR은 그 가운데 앱 쪽이다. 실행기 쪽(cron 없앰, `site-checks`의 push를 main으로 좁힘)은 다른 하위 세션이 실행기 저장소에서 한다. 앱 PR이 먼저 병합돼야 부르기 공백이 없다.
- 앱 저장소 자신의 수집을 부르는 일이라 GitHub 약관의 ‘저장소 프로젝트와 상관없는 일’에 들지 않는다(상위 세션 판단, 인계 문서 「상위 세션 인계」 4의 7). 바깥 예약기(Cloudflare Worker)가 매일 00:47Z에 실행기 catalog를 불러 그날 첫 수집을 여는 것은 그대로다.

## 겹침을 거르는 기존 장치(코드로 읽은 것, 2026-11-09 main `1fb15d3`)

`collect.yml`의 gentle 실행은 수집 전에 두 단계를 지난다. spare가 만든 run도 같은 run이라 둘 다 그대로 지난다.

1. 겹침 확인(C06, `scripts/collection-chain.mjs --overlap`, `overlapNow`): 이 run이 만들어질 때 main의 다른 gentle 수집 run이 대기·진행 중이었으면 `overlap=…`을 낸다. 앞 run이 성공으로 끝났어도 이 run이 만들어진 뒤에 끝났으면 같다. 앞 run이 실패·취소로 끝났으면 겹침으로 보지 않아 이 run이 수집한다(`collecting`의 `inFlightAt`). GitHub API를 읽지 못하면 겹침 없음으로 보고 수집한다.
2. 예산(C03, `scripts/collection-budget.mjs`): `OVERLAP`이 있으면 `pages=0`(`reason=overlap: …`)이다. 없으면 그날(UTC) 계정 D1 쓰기·읽기 사용량으로 쪽수를 정한다(상한 120쪽, 쓰기·읽기 각 85%). 0쪽이면 수집기를 부르지 않고 `snapshot` 배포와 `chain` job을 건너뛴다(`needs.collect.outputs.pages != '0'`). 사용량을 읽지 못하면 16쪽이다.
3. 줄 세우기: 최상위 `concurrency` 묶음 `yukemuri-catalog-updates`(`queue: max`, `cancel-in-progress: false`)가 run을 취소하지 않고 한 번에 하나씩 돌린다.

이어 부르기(`collect-chain.yml`, `nextRun`)에는 더 새 수집 run이 있으면 부르지 않는 규칙과 하루 24번 상한이 있다. 그 하루 24번은 0쪽으로 끝난 run도 센다.

## 결정

1. 이름은 `collect-spare.yml`로 했다. 실행 이름은 따로 두지 않았다. 이 workflow는 부르기만 하고, 감시와 매일 점검이 보는 이름 `Yukemuri collection (gentle)`은 부르는 `collect.yml`이 붙인다.
2. 수집을 바로 멈추는 스위치는 셋이고, 새 저장소 변수나 Secret은 필요 없다. Actions의 ‘Yukemuri collection spare’ 끄기, ‘Yukemuri collection chain’ 끄기(둘 다 Disable workflow 또는 `gh workflow disable`), 실행기 `YUKEMURI_ENABLED`=`false`다. 앞의 둘 가운데 하나만 끄면 다른 하나가 수집을 이어 가고, 셋째가 없으면 바깥 예약기가 매일 00:47Z에 여는 첫 수집이 날마다 한 번 돈다. 처음 쓴 문장은 ‘workflow 끄기가 스위치의 전부’라고 읽혀 이 셋째를 빠뜨렸다(PR 검토의 P2-2로 고침). 변수 없이 workflow 끄기를 먼저 고른 까닭은 사용자가 만들 값이 없게 하려는 것이다. `docs/cloudflare-deploy.md`의 ‘주의’ 5번에 적었다.
3. spare 안에 ‘gentle run이 진행 중이면 부르지 않기’ 같은 앞 검사를 넣지 않았다. 까닭은 셋이다. (가) `collect.yml`이 같은 일을 만들어진 run 안에서 이미 하고, 이 PR의 검사가 그것을 보인다. (나) 앞 run이 실패로 끝나면 줄 서 있던 spare run이 바로 수집해 고리를 잇는데(겹침 규칙의 `failed-blocks` 사례), 앞 검사가 그 run을 만들지 않으면 한 시간을 더 잃는다. (다) 같은 규칙이 두 곳에 생겨 어긋날 수 있다. 사용자의 ‘중복을 막는 장치는 넣는다’ 지시(10-21T07:3xZ)는 기존 장치가 이 호출도 막는지 검사로 확인하는 것으로 지켰다. 아래 ‘남은 일’ 1번의 최소 간격 장치는 C06의 규칙을 바꾸는 일이라 이 PR에 넣지 않았다.
4. `AGENTS.md` 충돌: ‘레포 구조 계획’ 줄은 ‘앱 레포 수집 workflow에는 cron을 두지 않는다. 예약은 실행기 레포에 남아 그 workflow를 부른다’고 쓴다. 사용자의 11-03T04:4xZ 결정이 매시간 예비만 앱 레포로 옮기라고 하므로 그 줄에 ‘`collect.yml` 자신에는 cron이 없고 매시간 예비만 `collect-spare.yml`로 옮겼다’는 한 문장을 더했다. 이 변경이 맞는지 상위 세션이 PR에서 본다.
5. cron 분은 실행기와 같은 37분이다. 이행 기간(이 PR 병합 뒤 실행기 PR 병합 전)에 둘이 같은 분에 와도 한 run이 먼저 수집하고 다른 하나는 0쪽이 된다(아래 모의).

## 60일 규칙

public 저장소의 예약은 레포 활동이 60일 없으면 GitHub가 자동으로 끈다. GitHub 문서 ‘Events that trigger workflows’의 schedule 절에서 직접 받아 읽었다(2026-11-09T12:08Z, `docs.github.com`): ‘In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days.’ `collect-watch.yml`에도 있던 위험이다. spare가 꺼져도 수집은 이어진다. 바깥 예약기가 매일 00:47Z에 실행기 catalog를 불러 그날 첫 gentle run을 열고, 그 run의 이어 부르기(C06)가 다음 run을 부르기 때문이다. 잃는 것은 고리가 끊긴 날 시간 단위로 다시 잇는 예비뿐이다. 12시간 넘게 성공이 없으면 `collect-watch.yml`이 알린다(그 workflow도 꺼졌으면 실행기의 12시간 확인이 남는다). workflow 주석(`collect-spare.yml`)과 `cloudflare-deploy.md`에 같은 내용을 적었다.
